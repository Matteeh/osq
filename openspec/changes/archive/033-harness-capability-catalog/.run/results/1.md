# Task 1 result — Harness catalog and exhaustive registration

## Changed

- Added `src/core/harness-catalog.ts`: one frozen catalog of the four supported
  harnesses (`agy`, `opencode`, `mock`, `codex`) with normalized lookup,
  ordered available names, per-entry executable/model/effort resolution,
  planner-agent capability (agent support, default agent, native brief
  fallback), `resolveExecutorIdentity`, and `resolvePlannerSelection`. Core
  imports only `type OsqConfig`, so `src/core` still never imports `src/harness`.
- `src/core/config-codex.ts`: planner validation now derives supported harness
  names and optional-setting support from the catalog (`findHarness` /
  `HARNESS_NAMES`), normalizes casing, keeps the required non-empty model, and
  names the selected harness plus offending setting on rejection. 032 resolver
  exports are now re-exported from the catalog rather than reimplemented.
- `src/core/config.ts`: `loadConfig` applies `OSQ_MODEL` through catalog entries
  instead of per-harness comparison branches; the agy section keeps the legacy
  “env applies even when unselected” behavior, codex/opencode apply only when
  selected, and explicit models still win. `defineConfig` behavior unchanged.
- `src/core/config-doctor.ts`: `harnessBinary` delegates to the catalog entry
  executable; `mock` returns `null`, uncatalogued names are echoed back.
- `src/harness/index.ts`: adapter map is typed `Record<HarnessName, () => HarnessAdapter>`
  (compile-time exhaustive) and exported as `harnessAdapterFactories`;
  `getHarnessAdapter` resolves through catalog lookup, normalizes casing, and
  reports ordered catalog names for unknown adapters.
- `src/index.ts`: re-exports catalog helpers/types plus `validatePlannerConfig`.
- Added `tests/harness-catalog.test.ts` and `tests/config-planner-catalog.test.ts`
  covering catalog uniqueness/immutability/order, normalized lookup, executable
  precedence, executor identity with native `default` and no cross-harness
  fallback, planner-agent capabilities, runtime factory parity, explicit and
  implicit planner selection, mixed harnesses, and public exports.

## Deviated

- `resolveHarnessModel('opencode', ...)` no longer falls back to the agy model.
  This is required by the acceptance line forbidding cross-harness fallback and
  is not covered by any existing assertion.
- `getHarnessAdapter`'s unknown-name error now lists catalog order
  (`agy, opencode, mock, codex`) instead of the old map order. Existing tests
  only match the prefix.
- Planner validation now accepts supported casing and returns the canonical
  lower-case harness name (delta scenario “any supported casing”).

## Drift against features

- None. The proposal reads `cli-foundation` and `watcher-and-harness`; both
  living specs already contain the 032 Codex requirements, and no feature doc
  was edited.
