## Acceptance

- [ ] `LandCommandOptions` and `GraphCommandOptions` extend `CommandInputs`; `MessageCommandOptions`, `SyncCommandOptions` and `SpecCommandOptions` are `CommandInputs`. None declares `cwd`, `config`, `stdout` or `stderr` itself.
- [ ] The five commands resolve their inputs through `resolveInputs` and load config at the same point as before, so a configuration error still becomes the same `CommandError`. They write the same raw text as before.
- [ ] New `tests/command-inputs-vcs.test.ts` runs `osq graph`, `osq graph --json`, `osq spec` and `osq spec <capability>` once through `runCliCaptured` and once directly with `cwd`, `config`, `stdout` and `stderr` writers that append to strings, and asserts the same stdout and stderr text both ways.
- [ ] The same test calls `syncCommand`, `messageCommand` and `landCommand` directly with a `cwd` that has no `osq.config.ts` and a passed `config`, and asserts each uses that config: sync with `vcs.enabled` off rejects with `osq sync needs vcs.enabled and git`, and message and land for an unknown id reject with the same `CommandError` message `osq message` and `osq land` print to stderr through `runCli`.
- [ ] Every existing land, message, sync, graph and spec test passes unchanged.

## Details

Pass `allowStale: true` and a temporary `packageRoot` to `landCommand` in
the test so the stale-build check does not decide the result.
