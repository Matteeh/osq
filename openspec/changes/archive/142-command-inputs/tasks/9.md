## Acceptance

- [ ] `InboxDispatchOptions` extends `CommandInputs` instead of declaring `cwd`, `config`, `stdout` and `stderr`, and `inboxDispatchCommand` resolves them through `resolveInputs`, loading config at the same point as before.
- [ ] The text view and the JSON document go to `stdout` as one write of the text plus `\n`. The card session and the follow loop always receive the resolved `stdout` and `stderr`.
- [ ] Both wait recorders get a `stderr` that writes the message plus `\n` to the resolved `stderr`, as `console.error` printed it before. The default inbox sound rings its bell through `stdout` and warns through `stderr` with `\n`, through `createInboxSound`'s `bell` and `warn` seams; a passed `sound` is used as given.
- [ ] `createTerminalInput(stream, stdout)` writes the `line` question to `stdout`, which defaults to `processStdout`; `inboxDispatchCommand` passes its resolved `stdout`.
- [ ] Through `runCli`, `osq inbox` and `osq inbox --json` without a terminal, and `osq inbox --follow --json`, print the same stdout and stderr as before and exit with the same code.
- [ ] New `tests/command-inputs-inbox.test.ts` runs `osq inbox` and `osq inbox --json` once through `runCliCaptured` and once directly with `cwd`, `config`, `stdout` and `stderr` writers and `isTerminal: () => false`, and asserts the same text both ways; it also asserts a wait-log failure line and a bell reach the passed writers.
- [ ] `tests/inbox-cards.test.ts` and `tests/inbox-dispatch.test.ts` expect the trailing newline their `stdout` writer now receives on the text and JSON views.
