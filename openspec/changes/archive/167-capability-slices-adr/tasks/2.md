# 016. Capability slices

Date: 2026-10-10

## Status

Accepted

## Context

osq's 8 living capabilities are horizontal layers, and their names differ from
their folders. cli-foundation owns `src/core/foundation/**`, all of
`src/cli/**`, `templates/**` and the guidance files. watcher-and-harness owns
`src/watcher`, `src/harness`, `src/core/run` and `src/core/lifecycle`. On
2026-10-10, no source file sat in a folder named after its capability, and 5
command files in `src/cli/` were owned by two capabilities.

A feature such as land or mcp touches `src/cli`, `src/core/<x>`,
`src/core/foundation` and often `src/watcher`. Of the 30 changes from 136 to
165, 22 wrote cli-foundation and 14 wrote watcher-and-harness; only 6 wrote a
single capability other than cli-foundation. So two changes to different
features usually write the same capability and the same files. They conflict
at sync, and stacking changes that share a capability would put about three
in four in one line.

Every feature also edits the same shared lists: `DEFAULT_CONFIG` in
`src/core/foundation/config.ts`, the command registration in
`src/cli/index.ts`, the help groups in `src/cli/help-groups.ts`, and the MCP
tools in `src/cli/mcp-tools.ts`.

The spec layout `openspec/specs/<capability>/spec.md` comes from OpenSpec, and
osq runs the pinned OpenSpec validator on it (ADR 004). Living specs are
rebuilt by replaying every archived delta in order, so moving a spec folder by
hand is undone by the next replay.

The layout follows known practice: package by feature rather than by layer,
Vertical Slice Architecture (Jimmy Bogard, 2018), Screaming Architecture
(Robert C. Martin, 2011), the Shared Kernel of Domain-Driven Design (Eric
Evans, 2003), modular monoliths such as Shopify's componentization with
Packwerk, and Feature-Sliced Design, whose shared layer may not import the
slices above it.

## Decision

1. **A capability is a feature, as a vertical slice.** Its code lives in
   `src/<capability>/`, which holds every layer the feature needs: its CLI
   command, its core logic, and its watcher, web and MCP hooks. The capability
   is named after that folder, and the folder after the capability. A small
   feature joins the nearest slice and is split out by a generated change when
   it grows. Slices do not nest, except kernel slices under `src/kernel/`.
2. **The kernel is slices too.** The code every slice may import lives in
   kernel slices, each its own capability in `src/kernel/<capability>/` with
   `group: kernel` in its `osq.yml`: `config` (loading, the merging of slice
   defaults, and the public config exports), `state` (the `.run/` paths and
   markers and the event log writer), `openspec` (the spec model: parse,
   delta, hash, apply), `git` (the git port), `cli` (the CLI entry and command
   registry) and `loop` (the watcher loop). One kernel capability would become
   the next cli-foundation, written by most changes. A kernel slice never
   imports a feature slice, except the registry importing each `slice.ts`.
   Harness adapters are not kernel; they are the `harness` slice.
   `src/index.ts` stays the package entry, owned by `config`.
3. **A slice registers itself.** Each slice exports one `slice.ts` naming its
   config defaults, commands with their help group, MCP tools and watcher
   hooks. One static list in the `cli` kernel slice imports every `slice.ts`,
   checked by a test against the folders. Adding a command, config block or tool to an
   existing slice edits no file outside it; adding a slice adds one line to that
   list. Config stays the only source of limits and timeouts.
4. **Code outside `src/` keeps its place.** Tests stay in `tests/`, and a new
   test for a slice is named `tests/<capability>-<topic>.test.ts`. Fixtures,
   templates, guidance files and `packages/ui` stay where they are, owned
   through each capability's Code ownership globs.
5. **Renames and splits are generated changes.** A capability is renamed or
   split only by a change whose deltas osq generates: every requirement
   REMOVED from the old capability and ADDED, byte for byte, to the new one.
   Replay then rebuilds the same living specs. Nobody renames a spec folder by
   hand, and archived changes keep their old capability names.
6. **The OpenSpec layout stays.** Living specs stay at
   `openspec/specs/<capability>/spec.md` with their `osq.yml`, and the
   validator stays as ADR 004 says.
7. **Moves go one slice per change.** Each move generates the rename or split,
   moves the files with their imports, and records the slice as moved in
   `tests/capability-slices.test.ts`. Until a capability's move lands, new code
   for it goes where its code is today.
8. **The checks test warns, then blocks.** `tests/capability-slices.test.ts`
   reports every file under `src/` that no capability owns, that two
   capabilities own, or whose owner is not named after its slice folder:
   `src/<x>/`, or `src/kernel/<x>/` under `src/kernel/`. A file directly under
   `src/` is judged only on its owners. It fails for a capability recorded as moved, and only warns
   for the others. When every living capability is recorded as moved, every
   finding fails.
9. **This is osq's own layout.** osq does not impose it on the projects it
   runs. A future lint check for other projects is opt-in config, off by
   default, because framework layouts, cross-cutting capabilities and small
   projects can lose more than they gain.

## Consequences

- Two changes to different features touch different capabilities and
  different folders, so stacking on a shared capability stacks only changes
  that can really conflict, and slices can run side by side.
- A capability name tells a reader the folder, and the folder tells the
  capability.
- osq goes from 8 capabilities to about 24, 6 of them kernel. Each split
  moves requirements, not text, so no requirement changes meaning in a move.
- Until the moves land, the checks test prints a long warning list. It shrinks
  with each move.
- `capability-rename-generator` and `slice-registries` come before the first
  move.

## Rejected

- **Renaming capabilities to match today's folders.** Cheaper, and no code
  moves, but the layers stay horizontal: cli-foundation and
  watcher-and-harness keep owning most changes.
- **Renaming `openspec/specs/` to `capabilities/`.** It breaks the OpenSpec
  layout and its validator (ADR 004). Revisit with the Rust rebuild.
- **A first-class rename delta.** OpenSpec has none, and replay, land and sync
  would all have to learn it.
- **Nested layer folders** such as `src/core/<capability>` and
  `src/cli/<capability>`. A feature would still span several top-level
  folders. `src/kernel/` is the one nesting, and it groups slices, not layers.
- **One kernel capability.** Config, git, the spec model and the CLI registry
  would share one capability, and most changes would overlap on it.
- **Moving everything in one change.** Too large to review, and every open
  change would conflict with it.
