## Acceptance

- [ ] New `src/core/report/approval-flags.ts` reads `approvalFlags` from `.run/manifest.json` in every active and archived change folder `getMetricsReport` walks. It skips folders whose manifest lacks a valid `approvalFlags`, and never recomputes flags.
- [ ] A change has trouble when any task stream under `.run/events/` has a `dead` event, or any task or `change` stream has a `regressed` event.
- [ ] `MetricsReport` gains `approvalFlags: { changes, byFlag }`. `changes` is the number of counted changes. `byFlag` has the five flag ids and `none` (changes with empty `ids`), each `{ shown: { fired, troubled }, confirmed: { fired, troubled } }`, always present with zeros.
- [ ] Text adds `Approval flags:` after the planning section: `  <changes> approved changes recorded flags`, then one line per key as `  <id>: fired <n> (shown <s>, confirmed <c>), later trouble <t> (shown <ts>, confirmed <tc>)`.
- [ ] `osq report --json` emits the field through `toStableMetrics`. `fixture/report/expected.json` gains it with zeros, since fixture manifests carry no flags, and changes nowhere else. In `tests/report-json.test.ts`, only key lists, hand-built reports, and the fixture comparison change.
- [ ] New `tests/report-approval-flags.test.ts` builds changes with recorded flags in both modes, with and without later `dead` and `regressed` events, plus one older manifest without the field, and asserts every count.

## Details

Import `ApprovalFlagId` from `src/core/spec/digest.ts` for the key list, so
the report and the digest cannot drift. Keep `report.ts` changes to wiring;
`getMetricsReport` and `formatMetricsReport` are grandfathered in the function
budget, so add helpers rather than growing them. A worktree measurement showed
that a new top-level report key breaks only `tests/report-json.test.ts` and
`fixture/report/expected.json`. Other tests are frozen.
