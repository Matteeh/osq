## Details

The watcher already leaves a change with `steering` alone, so the planner's edits in the worktree never cause a `worktree_dirty` halt; `.run/` files are allowed dirt. The run writes no inbox, dispatch or status code; task 4 reads the record. Nothing passes `steeringPrompt` from the CLI yet; task 5 does.

A rough version of this task, measured on 2026-10-13, passed the full suite except the function budget on a single 120-line `runAutoSteer`. In a rough end-to-end run the planner's forged `.run/approved` and its write to `src/out.txt` were put back, the record was `ready` with `changed` `["tasks/2.md"]`, a second pass spawned nothing, and task 2 ran after `osq approve 001`. Setting a task's verify to the planning sentinel gives `lint_red`. A steered change created without `brief.md` makes the prompt builder throw `ENOENT`, which the run must catch so the watcher pass goes on.
