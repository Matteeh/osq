## Changed

- `src/watcher/verify.ts`: `runVerificationGateResult` and `runVerificationGate`
  gained an optional `config?: OsqConfig` as their last argument and pass it to
  `runVerificationCommand` as `{ config }`. Existing 3- and 4-argument callers
  are unchanged.
- `src/watcher/runner.ts`, `src/watcher/task-verify.ts`,
  `src/watcher/change-verify.ts`, `src/watcher/archive-verify.ts`: each task,
  pre-spawn, change, and archive verify passes the config it holds.
- `src/watcher/baseline.ts`: the baseline verify passes `{ config }`.
- `src/watcher/mutation-check.ts`: `runPicks` takes the config and forwards it
  as `runMutationPick`'s last argument.
- `src/watcher/regression.ts`: `ScopeAuditOptions` gained `config?: OsqConfig`;
  the stale-task verify passes it to `runVerificationGateResult`, and
  `guardScopeRegression` passes its config to `auditScopeRegressions`.
- `tests/watcher-verify-role-env.test.ts`: runs one task through
  `runWatcherOnce` with a `defineConfig` config setting `gates.baselineVerify`
  and `confinement.roles.verify.env: ['VERIFY_PROBE']`. It sets `VERIFY_PROBE`
  and `SECRET_PROBE` on `process.env` for the test only and restores both after.
  The baseline, every task verify, and every change verify exit 0, the task is
  done, and the post-spawn task verify output is the change folder.

## Deviated

- `runVerificationGate`'s projection was rewritten as
  `const { passed, timedOut, error } = await runVerificationGateResult(...); return { passed, timedOut, ...(error ? { error } : {}) };`.
  `tests/runner-synthesized-result.test.ts` deep-equals the gate result and caps
  `verify.ts` under 200 lines, so the same result shape had to fit in fewer
  lines. Behavior is unchanged.
- `auditScopeRegressions` passes `config` to the verify gate through the
  existing `context` argument (`config` in the context object) and via the new
  fifth argument. The gate call is written with short locals
  (`command`, `timeoutSeconds`, `gateContext`) so `regression.ts` stays within
  its 250-line cap; the return value is identical.

## Missing context

- Neither `verify.ts`'s 200-line budget (`tests/runner-synthesized-result.test.ts`)
  nor `regression.ts`'s exact line pressure was named in the task, though both
  bound how the config argument can be threaded.

## Outside scope

- `src/watcher/loop.ts` and `src/watcher/archiver.ts` also call
  `auditScopeRegressions` but are outside this task's scope and still pass only
  `limits`, not `config`. The scope-regression verifies those two calls trigger
  therefore keep the default empty verify environment. Adding `config,` to their
  `auditScopeRegressions` calls is a one-line change each and should be done in a
  task that owns those files.
