## Changed

- `src/harness/claude/claude-exec.ts`, `src/harness/pi/pi.ts`,
  `src/harness/codex/codex.ts`, `src/harness/agy/agy.ts`, and
  `src/harness/opencode/opencode.ts` now import `buildRoleEnv` from
  `../../core/run/role-env.js`. Each task spawn passes
  `buildRoleEnv('agent', { config, harness: <adapter name>, extraEnv: { OSQ_TASK_NUMBER, OSQ_SPEC_FOLDER } })`
  instead of spreading `process.env`. Interactive sessions, version probes,
  and session exports are untouched, so they keep osq's environment.
- `src/harness/claude/claude-exec-args.ts`: `CLAUDE_BASE_ARGS` adds
  `Bash(curl:*)`, `Bash(wget:*)`, `Bash(ssh:*)`, `Bash(scp:*)`, and
  `Bash(sudo:*)` after `Bash(git:*)`, before `--strict-mcp-config`.
- `src/harness/opencode/opencode.ts`: `OPENCODE_AGENT_TEMPLATE`'s `bash`
  became a map with `"*": allow` and `"git"`, `"git *"`, `"curl *"`,
  `"wget *"`, `"ssh *"`, `"scp *"`, `"sudo *"` each `deny`; `read`, `edit`,
  `glob`, `grep`, `webfetch`, and `websearch` are unchanged. Setup still only
  refreshes the managed block, so an existing file's frontmatter stays.
- `tests/claude/exec-adapter.test.ts`: `BASE_ARGS` gains the five new deny
  rules. No other line changed.
- `tests/opencode-setup.test.ts`: the permission test's title now says bash is
  a map that denies git and network tools, and its `perms.bash` assertion is a
  deep-equal to the map. The idempotency fixture still writes `bash: allow`.
- Added `tests/agent-role-env.test.ts`. It writes a 0o755 `#!` fake binary
  that prints a version and otherwise records `JSON.stringify(process.env)` to
  `OSQ_FAKE_ENV_RECORD`. It covers the claude task environment (ANTHROPIC_API_KEY
  and both osq extras present; OPENAI_API_KEY and SECRET_PROBE absent), the
  codex configured agent name (AGENT_PROBE present, SECRET_PROBE absent), the
  pi spawn (SECRET_PROBE absent), an existing opencode agent file keeping
  `bash: allow` through `setup`, and that the five adapter sources contain no
  `...process.env`. Probe variables are set on `process.env` per test and
  restored afterwards.

## Deviated

- The acceptance names the `buildRoleEnv` options property `extra:`, but the
  interface task 1 landed in `src/core/run/role-env.ts` calls it `extraEnv`.
  `role-env.ts` is in this task's `entry`, not its `scope`, so I used
  `extraEnv` in all five adapters instead of editing the entry file. The
  behavior is identical: extras are set last and win.

## Missing context

- Nothing blocked the work. Had the task's `extra` spelling matched
  `role-env.ts`, the first run would not have failed on `OSQ_TASK_NUMBER`.
