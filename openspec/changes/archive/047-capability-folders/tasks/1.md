## Details

This task moves nothing. It exists so the next task's file moves cannot break a
package-root path silently: after the moves, `package-root.ts` is the only
place whose relative URL gains one `../`, and this test catches a wrong one.

The five current copies all compute the root with
`new URL('../../', import.meta.url)` or `new URL('../../templates', ...)`.
Keep that exact form in `package-root.ts` (it resolves correctly under tsx from
`src/core/` and compiled from `dist/core/`), and derive `TEMPLATES_ROOT` from
`PACKAGE_ROOT` with `path.join`. Keep the existing explanatory comment from
`manifest.ts` about tsx and `dist/` on the new constant, and drop the now-unused
`fileURLToPath` and `path` imports only where a file no longer uses them.

The recursive walk must match files by base name `package-root.ts` at any
depth, because the next task moves the file to `src/core/foundation/`.
Import `package-root.ts`, `init.ts`, and `new.ts` in the test through relative
specifiers such as `../src/core/package-root.js`; the next task rewrites them.

Do not touch `src/core/config.ts`. `loadConfig` passes an absolute path to
`jiti.import`, so the base given to `createJiti` does not decide which file
loads; the proposal records this. `src/watcher/dev.ts`, `src/watcher/build.ts`,
and `src/cli/index.ts` also compute roots from their own location, but they do
not move and are outside this task's scope.

This task's `scope` is authoritative over any injected code-ownership rules for
the duration of change 047; those rules still name the old flat paths.
