## Changed

- Added `src/core/vcs/sync-lockfiles.ts`:
  - `blockedConflicts`, moved from `sync-main.ts`, now also leaves out every conflict path whose `lockRebuildCommand` is non-null, so a rebuildable lock file is not a code conflict.
  - `rebuildLockfiles`, step 3's lock file rebuild. In path order it writes the default branch's copy with `vcs.show`, runs the rebuild command in the lock file's folder through `runVerificationCommand` with `{ role: 'prepare', config }` bounded by `timeouts.verifyTimeoutSeconds`, and stages the lock file. A failed command throws a `SyncStop` with reason `sync_failed` and the requirement's message plus the last `limits.cardOutputLines` lines of output.
  - Both exports carry the `@scenario` and `@adr 017` tags for the scenarios they serve.
- `src/core/vcs/sync-main.ts` now imports both helpers, calls `rebuildLockfiles` in `finishSync` right after `rebuildLivingSpecs` and before `runPrepare`, keeps `syncWithDefaultBranch`'s signature, and drops to 232 lines.
- Added `tests/vcs-sync-lockfile.test.ts`, one `it` per scenario under a `Default branch sync` describe, on scratch repositories with an active `002` worktree: a clean Cargo workspace lock rebuild, a lock file beside a code conflict, and a hand-written lock file whose rebuild fails. It asserts the clean `synced` commit, the rebuilt lock holding both crates with `cargo metadata --offline --locked`, the `sync_conflict` stop naming only `src/app.txt`, the `sync_failed` rebuild stop, and an unchanged HEAD and status on both stops.
