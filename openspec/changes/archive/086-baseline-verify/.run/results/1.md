## Changed

- `src/core/foundation/config-gates.ts`: `GatesConfig` gains optional
  `baselineVerify`. `validateGatesConfig` reads it, throws
  `gates.baselineVerify must be a non-empty command` for a non-string or
  whitespace-only value, keeps the trimmed command, and omits the key from its
  result when unset (spread of an optional field), so existing deep-equality
  checks of `gates` are unchanged.
- `src/watcher/baseline-key.ts` (new): exports `BaselineKey` (`commit`,
  `treeDigest`) and `readBaselineKey(vcs, projectRoot)`. It returns null under
  `NoVcs` or when HEAD has no commit, otherwise HEAD's sha plus a SHA-256 digest
  over each status entry outside any `.run/` segment, as
  `path\0code\0contentHash` (null content for a deleted file), sorted by path.
  Content hashes come from `hashFileContent`.
- `tests/baseline-key.test.ts` (new): covers both configuration scenarios
  through `loadConfig` in a temporary project (trimmed command, empty command
  rejected) plus the unset-key case and `validateGatesConfig` omission; covers
  the key scenarios against temporary git repos via `selectVcs` (unchanged tree
  with a `.run/` write in between, edited tracked file, changed untracked file,
  no key outside git, no key with no commit).

## Missing context

The cli-foundation delta's "Empty command" scenario says loading fails, but
`loadConfig` catches only errors thrown while jiti imports the config module; a
raw exported object is validated by `defineConfig` after that catch, so the test
writes `export default { gates: ... }` (not `defineConfig(...)`) to observe the
throw. Worth noting for task 2 in case it wants `defineConfig`-wrapped fixtures.

## Outside scope

`loadConfig` silently swallows validation errors thrown inside a config module
that calls `defineConfig` at import time, so such configs fall back to defaults
instead of failing. Pre-existing behavior, left alone.
