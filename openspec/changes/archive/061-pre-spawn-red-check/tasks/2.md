## Acceptance

- [ ] On attempt 1 (from `readRetryContext`), with `gates.preSpawnVerify` absent or `warn`, `runTask` runs the task's `verify` after `captureTestGate` and before the `measures` start event, under `timeouts.verifyTimeoutSeconds`, through `runVerificationGateResult`. That appends one `verify_ran` event whose data adds `phase: "pre_spawn"`, `expected` (the task's `verifyStarts`), and boolean `mismatch` to the usual fields. Post-spawn, change-level, scope-audit, and archive `verify_ran` events stay unchanged.
- [ ] `mismatch` is true when `red` is expected and verify passed, or when `green` is expected and verify failed or timed out. It is never true for `any`.
- [ ] Under `warn`, a mismatch calls `logger.warn` once with a line naming the task number, the expected start state, and the exit code, then the task continues through spawn and its normal gates. A matching start logs no warning.
- [ ] Under `fail`, a mismatch writes `.run/dead/<n>.md` with `reason: verify_precondition`, the command, `expected`, the exit code, and the captured output. It appends a `dead` event with that reason and returns `{ success: false, reason: 'verify_precondition' }`. No `measures`, `started`, or agent spawn follows. `RunTaskFailureReason` includes `verify_precondition`.
- [ ] Under `off`, no pre-spawn verify runs. A task whose event stream already holds a `retry` event with `attempt: 2` runs no pre-spawn verify.
- [ ] `tests/fixtures/events/verified.jsonl` and `dead.jsonl` are regenerated with `UPDATE_GOLDEN=1`. Each gains only the leading pre-spawn `verify_ran` line: `mismatch: true` for the verified task, `false` for the dead one.
- [ ] `runner.ts`, `verify.ts`, and `outcome.ts` stay under 200 lines (`tests/import-graph.test.ts`). No function outside the grandfather list passes 80 lines.

## Details

Put the check in the new `src/watcher/task-verify.ts`. That includes the
attempt lookup, the mode switch, the mismatch rule, the warning, and the
`verify_precondition` marker text. `runTask` calls it with one short call and
passes the failure through its existing `fail` helper. `runner.ts` has only a
few lines of headroom. If it would reach 200, also move the existing post-spawn
`verify_red` marker text out of `runTask` into `task-verify.ts`, unchanged.
`verify.ts` has five lines of headroom. Let `runVerificationGateResult`'s
context accept extra event fields computed from the result, and keep the rule
itself in `task-verify.ts`. Add the three optional fields to
`VerifyRanEventData`.

Put new tests in `tests/pre-spawn-verify.test.ts`. Drive the real `runTask` on
an approved change in a temp project, as `tests/runner-test-gating.test.ts`
does, with local verifier scripts written into that project. Use one that
always passes, one that always fails, and one that passes only once the agent
has written a flag file. Define a small adapter in the new test file that writes
the flag file and the result file. The flip verifier shows the expected-red
path running end to end to `done`. Pass a stub `Logger` to capture warnings. Do
not edit any preexisting test outside `tests/fixtures/events/`.
