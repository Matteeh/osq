The nine golden files this task must create cannot be written without a
scope violation, so the task cannot be finished within its scope as it
stands.

`tasks/3.md` declares them with a brace pattern:

```
crates/kernel/storage/tests/golden/{pauses,recertifications,notices,focused_runs,mutation_picks,mutation_survivors,validator_runs,validator_findings,link_findings}.json
```

osq's scope resolver does not expand braces. `globToRegExp` in
`src/core/run/scope.ts` supports only `*`, `**`, `?` and a trailing `/`, and
`isPatternEntry` treats an entry as a pattern only when it holds `*` or `?`.
This entry has neither, so it is taken as a single exact path that matches no
file. `beginGitGuard` (`src/watcher/git-guard.ts`, `scopeViolations`) then
reports every file under `crates/kernel/storage/tests/golden/` as outside
scope, and the task dies `scope_violation`. That is exactly how attempt 1
died; its dead marker lists those nine files, and the `scopeHashes` of its
`measures` event records the brace entry itself with `before`/`after` null.

Verified against the built resolver:
`scopeCoversPath([...brace entry...], "crates/kernel/storage/tests/golden/pauses.json")`
is `false`, while the exact `tests/history_corpus.rs` entry and the
`tests/fixtures/history-cases/**` entry both resolve. The guard exempts only
a new untracked file directly under the repository's root `tests/`, so these
crate paths are not exempt either.

The fix is a scope change only: list the nine files, or write
`crates/kernel/storage/tests/golden/**`, in `tasks/3.md`, then re-approve
the change (editing the task file changes the sealed folder hash, so a plain
re-approve is not enough). Once the scope covers the path, the work itself is
small and known: copy the nine files byte-for-byte from the change's
`golden/` folder, add `tests/history_corpus.rs`, and add a fast case under
`tests/history_cases.rs` with a fixture under `tests/fixtures/history-cases/`
only where a golden row disagrees.
