## Acceptance

- [ ] Public configuration exposes a validated `gates.changeVerifyAfterTask` boolean, defaults it to `true`, preserves a partial `{ changeVerifyAfterTask: false }` override, and makes the doctor config check reject a missing or non-boolean resolved gate.
- [ ] After the task verify passes and the gate is enabled, `runTask` reads the proposal verify and runs it with `timeouts.verifyTimeoutSeconds` before any done marker, done event, or checkbox update.
- [ ] Incremental change verification delegates to the existing verification event path with target `change`, while the task stream retains its ordinary task verify and terminal lifecycle events.
- [ ] A non-zero or timed-out change verify returns `change_verify_red`, writes no done state, and records a task dead marker containing the command, numeric exit code, timeout state when applicable, and captured failing output.
- [ ] A failing task verify remains `verify_red` without running the proposal command, while disabling the new gate preserves successful task completion after task verification alone.
- [ ] `RunTaskFailureReason`, dead-event recording, retry, reporting, and outcome logging accept `change_verify_red` without special-casing it or changing `verify_red` and `scope_regression` behavior.
- [ ] `runner.ts` and `outcome.ts` remain strictly under 200 lines, `config.ts` remains within its 250-line budget, archive-time verification stays unchanged, and all frozen golden/import/budget tests pass.

## Details

Reuse `parseSpecMdFromFolder` to obtain the proposal verify and
`runVerificationGateResult` to retain command, exit code, output, duration, and
timeout state while emitting exactly one `verify_ran` event. Pass
`{ specFolderPath, taskNumber: 'change' }` for that event; do not duplicate the
event writer or change `archiver.ts`. Put proposal parsing, gate execution, and
marker formatting in the new `change-verify.ts` helper so `runner.ts` remains a
short orchestrator. Invoke it only after the existing task gate succeeds and
before `writeDoneMarker`.

Extend `RunTaskFailureReason` in `outcome.ts`; the existing `fail` path remains
the single dead-marker and dead-event writer. Preserve the marker's full
captured output, including failing test lines, and use a deterministic fallback
when output is empty. A missing proposal verify is approval-invalid already;
handle an unexpected missing parse as a failed change gate rather than silently
completing the task.

Add a small `config-gates.ts` under the `src/core/config*.ts` scope for the
gate type, default, merge, and boolean validation. Integrate it with
`DEFAULT_CONFIG`, `OsqUserConfig`, and `defineConfig`, and make `validConfig` in
`doctor.ts` require the resolved boolean. Keep `config.ts` under its existing
line budget by extracting gate-specific logic rather than expanding the module
past 250 lines. Tests should inject local proposal verifiers that append or
fail deterministically, assert ordering and event-file targets, and avoid
running this repository's `pnpm verify` recursively.
