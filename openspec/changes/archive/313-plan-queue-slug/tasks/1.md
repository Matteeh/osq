## Acceptance

- [ ] `osq plan --next <slug>` plans the named queue item and refuses as cli-foundation "Next queue item planning" says; `--next` with no slug selects as before.
- [ ] `prepareQueuePlan` takes an optional `slug`; the row choice, with and without a slug, lives in the new `src/core/status/queue-pick.ts`, so `queue-planning.ts` stays within the line budget with no new allow-list entry.
- [ ] `--run` still refuses `--next` with or without a slug, and the remote server's plan check treats a slug as next mode.
- [ ] New `tests/queue-plan-slug.test.ts` proves "Named queue item" and every row of "Named queue item refused" through `planCommand` with `print: true`, building queues as `tests/queue-plan.test.ts` does; every existing test passes unchanged.
- [ ] `prepareQueuePlan` and each new exported function carry `@scenario cli-foundation: Named queue item` and `@scenario cli-foundation: Named queue item refused` tags where they serve them.

## Details

Declare the commander option as `--next [slug]`, so `options.next` is
`true` without a value and the slug string with one; `PlanCommandOptions.next`
becomes `boolean | string`. Pass it through `prepareQueueSelection` rather
than adding lines to `plan.ts`, which sits at 249 of its 250 lines. Read
`osq plan --next` call sites that compare `next === true` (`plan-run.ts`
and `remote-commands.ts`) and make them accept a slug.

Take each refusal's state, change id and unmet dependencies from the
`QueueRow` that `readQueueState` already gives. The rejected-item and
spend checks run after the slug checks, unchanged. Write the tests with
`node:test`, not `scenario()`, as the proposal's assumptions say.

- cli-foundation: Named queue item
