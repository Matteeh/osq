Acceptance status: all seven lines satisfied except the literal ordering in
line 5 (see Deviated).

## Deviated

- **Start emission position.** Acceptance line 5 says "after the started event
  and before `spawnTaskAgent` returns". The `started` event is written
  asynchronously from inside `spawnTaskAgent` (`src/watcher/spawn.ts`), which is
  outside this task's scope, so runner code cannot run after it and before
  spawn returns. Emission happens immediately **before** `spawnTaskAgent`,
  matching the task Details ("between lock acquisition and `spawnTaskAgent`")
  and the intent of a start baseline. Stream order is therefore
  `measures → tokens → result_written → started` (started is delayed by its
  internal async build-info read).
- **`emitMeasures` signature.** Implemented as
  `emitMeasures(specFolderPath, taskNumber, data: MeasuresEventData)` rather
  than `(…, phase, data)`, because acceptance line 2 declares `phase` on
  `MeasuresEventData`; a separate `phase` parameter would be redundant.
- **Proposal read location.** `resolveChangeDoc` + read of the proposal lives in
  `measures.ts` (`gatherStartMeasures`) instead of `runner.ts`. This keeps
  `runner.ts` at 196 lines, under the `< 200` budget enforced by
  `tests/import-graph.test.ts`; the task Details only specified the read, not
  where it must live.
- **`scopeHashesBefore` deferred to task 3.** The task Details mention taking a
  scope-hash snapshot at start, but start-phase `MeasuresEventData` carries no
  `scopeHashes` and `noUnusedLocals` would reject an unused local. Task 3's
  acceptance explicitly owns the before/after snapshots, so it is added there.
- **Extra `gatherStartMeasures` orchestrator** (suggested by task 3's Details)
  keeps the runner small while `emitMeasures` remains the only write path.
