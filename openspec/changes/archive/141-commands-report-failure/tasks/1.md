## Acceptance

- [ ] `LintCommandOptions` has no `exit` option, and `lintCommand` sets no `process.exitCode`.
- [ ] When any linted change is invalid, `lintCommand` prints its findings, repository count or JSON document exactly as today, then throws `new CommandError('', { exitCode: 1 })`. A valid run returns `{ valid, entries }` as today.
- [ ] Through `runCli`, `osq lint` on an invalid change prints the same stdout and stderr as before this task and exits 1; on a valid change it exits 0.
- [ ] New `tests/lint-command-error.test.ts` covers the three lines above, the direct call with `assert.rejects` and the CLI path with `tests/cli-capture.ts`, and asserts `process.exitCode` is unchanged after the direct call.
- [ ] Every test that passed `exit` to `lintCommand` or read the exit code it set now expects the thrown `CommandError`: the `*lint*` tests, `proposal-writes-schema`, `validator-missing`, `steering-plan` and `steering-plan-default-branch`. In `impact-lint` and `steering-plan-default-branch` change only the `lintCommand` calls; task 2 and task 3 change their `doctorCommand` and `landCommand` calls.

## Details

The message rule is in the delta "Command errors": lint prints its failure as
a report, so the message is empty. Update `lintCommand`'s doc comment, which
mentions the exit sink.
