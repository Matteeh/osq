## Changed

- `src/core/status/inbox.ts`: added the `autopilot-stopped` needs-you kind and the optional `autopilotStopped: { reason, item, change: string | null, detail: string | null }` field. Inlined the old `showCommand` helper at its two call sites so the file stays at 249 lines within the source budget.
- `src/core/status/inbox-projection.ts`: `readInbox` now reads task 2's `readAutopilotStop` and adds one `autopilot-stopped` item next to the validator-failing item. The change title is read from the matching folder in `listChanges` (matched with `matchesFolder`), and before a change exists from the queue's item slug, falling back to the change id or slug when the title cannot be read.
- `src/core/status/inbox-text.ts`: renders `<id>: <title> — autopilot stopped: <reason>`, then `: <detail>` with whitespace collapsed when there is a detail, then ` — <command>`.
- `src/cli/status.ts`: adds `Autopilot stopped at <item>[ (change <id>)]: <reason> — <command>` as the last status line when a stop record exists.
- `packages/ui/src/home/labels.ts`: labels `autopilot-stopped` as `autopilot stopped`.
- New `tests/autopilot-inbox.test.ts` proving both stop-in-the-inbox scenarios, the no-stop scenario, the stop-in-status table, and the label, all against temporary projects with `statusCommand` given a temporary `home`.

## Deviated

The new test uses plain `node:test` cases instead of `scenario(...)` from `@matteeh/osq/testing`. The helper's lookup throws `The status-inspection spec has two scenarios named "Archived change that needs steering"` for every status-inspection scenario because the living spec repeats that name, so it cannot resolve these scenarios. Tasks 1 to 3 of this change reported and took the same route. The expected values are transcribed from the delta spec's THEN lines and table, not from running the code.

`autopilotStopped.detail` is `null` when the stop record has no body; the spec names the field but not its absent value.

## Missing context

None.

## Outside scope

`openspec/specs/status-inspection/spec.md` holds two scenarios named `Archived change that needs steering` (under `Change next step` and `Dispatch items`), which makes the traceability `scenario(...)` helper refuse every status-inspection lookup. Left alone; it belongs to no task in this change.
