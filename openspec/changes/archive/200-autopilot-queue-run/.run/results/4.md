## Changed

- New `src/watcher/autopilot.ts`: the `AutopilotCommands` port (`planNext`, `plan`, `approve`, `land`) and `runAutopilotPass(projectRoot, config, commands, { logger })`. The pass reads task 3's `readAutopilotView`, turns it into one `autopilotStep`, and takes that step once. It holds a stop that names the same item and change while the step is `plan-next`/`plan`/`approve`/`land`, clears any other record first, and writes one stop record otherwise (skipping an identical one). `plan-next` calls `planNext`, finds the new change through `readQueueState` and writes `.run/autopilot.md` with the queue approval's hash (or writes `plan_refused` when it cannot); `plan` adds `planner_started_at` then calls `plan`; `approve` adds `approved_at` then calls `approve`; `land` calls `land`. A throwing command writes `plan_refused`/`planner_not_ready`/`approve_refused`/`land_stopped` with `osq plan --next`/`osq plan <id>`/`osq approve <id>`/`osq land <id>` and the error's message or `exit code <n>`. Every step and every stop logs one `autopilot: ` line through the watcher's logger.
- New `src/cli/autopilot-commands.ts`: `createAutopilotCommands(cwd, config, options)` builds the port from `planCommand`, `approveCommand` and `landCommand` with no-op `stdout`/`stderr`. `planNext` is `plan --next`; `plan` runs `planCommand(id, { run: true, planRunRole: 'worker', adapter })` in process when an adapter is given and the detached `osq plan <id> --run` otherwise; `approve` passes `planningReaders`; `land` passes `allowStale` and `home`.
- `src/watcher/loop.ts`: `StartWatcherOptions` gains `autopilot?`; `runWatcherOnce` gains an optional 7th `autopilot` argument; both run `runAutopilotPass` after each `runWatcherCycle` when the port is given and `config.autopilot?.enabled` is true, and `runWatcherOnce` cycles again while the pass took a step. `runWatcherCycle` is unchanged.
- `src/cli/watch-service.ts`: `runWatcher` passes `autopilot: createAutopilotCommands(inputs.cwd, config)` to `startWatcher` (terminal, worker and `--once`).
- New `tests/autopilot-run-support.ts`: builds a temporary git project with `vcs.enabled`, the queue budgets, `gates.autoRetries` 0 and a `node verify.cjs` verifier, and `openspec/queue.md` with three items each depending on the one before. `AutopilotPlanner` writes a lint-green plan (replaces the sentinel verify and scopes the one task to `src/<slug>.txt`) as `scratchPlanner` does; `LintRedPlanner` leaves the plan red; `recordingCommands` records calls. Reuses `git`/`writeAt` from `tests/recovery-support.ts`, unchanged, and the test reuses `ScriptedAdapter`, `subjects` and `exists` from it.
- New `tests/autopilot-run.test.ts`: 9 tests, one per scenario, driving the queue through `runWatcherOnce` and the port `createAutopilotCommands` builds, except the two land scenarios.

## Deviated

- The tests are plain `node:test` tests, not `scenario(...)` from `@matteeh/osq/testing`: the `watcher-and-harness` and `cli-foundation` capabilities are not opted in by osq's own config (`traceability.capabilities: ['traceability']`), and task 3 found the status-inspection lookup throws on a duplicated scenario name. Expected values come from the delta specs, not from running the code.
- "A stopped land is not retried" and "A failed land with an exit code" drive the queue to the archived change with a real port wrapped so only `land` throws, then (for "not retried") call `runAutopilotPass` with a recording fake port and assert no command runs. The task said "run the pass with a fake port whose land throws"; wrapping the real port is what lets the queue reach the `land` step without a second copy of the flow.
- "Restart mid-queue" simulates the first watcher stopping after the first land by making its `planNext` throw (the pass records a `plan_refused` stop and the loop ends), then clears the stop and runs a fresh `runWatcherOnce` with fresh `createAutopilotCommands`, so "the first is not planned again" is asserted from the default branch's single `osq: 001 ` commit.
- "A human's step clears the stop" writes the `halted` stop by hand and leaves a live running lock in the approved worktree change, as the task's detail allows, then runs `runWatcherOnce` so the pass (step `wait`) clears the record and takes no step.
