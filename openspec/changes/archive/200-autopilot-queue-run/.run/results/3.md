## Changed

- New `src/core/status/autopilot-marker.ts`: the `AutopilotMarker` type, `autopilotMarkerPath`, `readAutopilotMarker`, `writeAutopilotMarker` and `updateAutopilotMarker`. The marker is `<changeFolder>/.run/autopilot.md`; the frontmatter holds `item`, `queue_approval` and `created_at` first, then `planner_started_at` and `approved_at` once autopilot reaches them. A missing or unparsable file reads as `null`, and updating a missing marker returns `null` and writes nothing.
- New `src/core/status/autopilot-view.ts`: `readAutopilotView(projectRoot, config)` reads the queue file's existence and parse error, whether any active change holds a pause `readActivePause` reports, the ids of active approved changes, and the first queue row whose state is not `landed` with its `item`, `row`, `approval` (task 2's `itemApproval`), and, when the row has an active or archived change, that change's `id`, `folderName`, `folderPath`, `location`, `approved`, `marker`, `planRun` (`currentPlanRun`) and `nextStep` (`readNextStep`). Everything is read from files.
- New `src/core/status/autopilot-step.ts`: `autopilotStep(view)`, the pure function from "Autopilot next step". It walks the spec table's rows in order: `done` (no queue file, or nothing open), `stop queue_unreadable` (parse error as detail), `wait` (active pause), `wait` (another approved change), `stop not_approved`/`changed_since_approval` (`osq queue approve`), `stop rejected` (`osq plan --next --replan`), `plan-next`, `wait` (unapproved change without a marker), `plan`, `wait`/`approve`/`stop planner_not_ready` from the planner run, `wait` (started with no current run), `wait` (approved change running/blocked), `stop halted` (the next step's command, and its detail when set), and `land`. Act steps carry the item's slug and change id; `plan-next` carries no change id; `stop` carries the reason, item, change and command.
- New `tests/autopilot-step.test.ts`: 21 tests. "Autopilot steps" is one test per spec table row (18), asserted in table order against hand-built views, with the queue-file, approval and `ready` plan-run rows read from temporary projects without git; plus the marker round trip on a temporary folder and a missing/unparsable-marker test.
- `pnpm verify` passes (EXIT=0), the task verify passes 21/21, and no file outside the task `scope` changed.

## Deviated

The task's scenarios are tagged in the source doc comments, but the test does not call `scenario(...)` from `@matteeh/osq/testing`. `lookupScenario` throws `The status-inspection spec has two scenarios named "Archived change that needs steering"` for every status-inspection lookup, because the living spec holds that name twice, so the scenario helper cannot look up either scenario this task proves. The two previous tasks in this change (tasks 1 and 2) likewise used plain `node:test` tests, so the test transcribes the delta spec's state/step table into `STEP_ROWS` in table order and asserts each row, which is the acceptance line's contract. Expected values come from the spec's table, not from running the code.

`AutopilotStep` is one flat shape (`kind`, `item`, `change`, `reason`, `command`, `detail`) with nullable `item`/`change`/`reason`/`command`, rather than a nested stop object, so a watcher can read one interface. `done` and `wait` name an item only when the state names one.

## Missing context

The task said "one `stop` carries a stop task 2's `autopilot-stop.ts` can write, with reason, item, change and command" but did not pin the step's exact type, so task 4's author must read this module for the shape it consumes.

## Outside scope

`openspec/specs/status-inspection/spec.md` holds two scenarios named `Archived change that needs steering` (requirements `Change next step` and `Dispatch items`), which makes the traceability scenario helper's lookup throw for every status-inspection scenario. I left the living spec alone; it belongs to no task in this change.
