## Changed

- `src/core/spec/linter.ts`:
  - Imported `verifyRunners` and `type VerifyRunner` from
    `../../kernel/languages/presets.js`.
  - `analyzeVerifyCommand` now takes a new optional last parameter
    `runners: readonly VerifyRunner[] = []`. After the sentinel and
    package-script checks it returns `unresolved: false` when the first token
    is a runner's binary and the second is one of that runner's subcommands
    (new `isRecognizedVerifyRunner` helper). `src/core/status/next-step.ts`
    still calls it with three arguments and is unchanged.
  - `chainedVerifyError` takes `hasPackageJson` and picks the package-script
    advice when set and the `scripts/verify.sh` advice otherwise.
  - `lintChangeFolder` reads `readLanguageMap(projectRoot, config)` once near
    the top, before the proposal verify check, and uses that one map for
    `gatedTestPathFilter` and `verifyRunners(languageMap.languages)`. It also
    reads whether the root holds `package.json` with a separate `pathExists`
    access (not `readRootPackageScripts`, which also yields no scripts for a
    malformed manifest), and passes that to `chainedVerifyError`. The later
    duplicate `readLanguageMap` for the frozen-test gate is gone.
- `tests/lint-cargo-verify.test.ts`: new. Scaffolds a project with
  `scaffoldProject`, `installFakeValidator`, `verify.cjs`, and the row's root
  manifest, with no git and no `cargo`. Proves "Cargo verify" with one case
  per row (including the `cargo doc` and `cargo test`-under-`package.json`
  warnings), and the two chained-verify scenarios with the exact spec strings.
- `tests/lint-findings.test.ts`: only the chained-verify expected string
  changed to the `scripts/verify.sh` advice, since that scaffolded project
  holds no `package.json`.

## Deviated

The three scenarios are proven with plain `node:test` `describe`/`it` rather
than the `scenario` helper. `lookupScenario('spec-lint-and-approve', ...)`
throws before reaching any scenario, because the living
`openspec/specs/spec-lint-and-approve/spec.md` already holds two scenarios
named "Python-only repository" (in "Import graph" and "Import graph built once
per lint run"), and duplicate-scenario detection runs over the whole living
spec. The task's acceptance only asks the new test to prove the scenarios with
the exact spec strings, and every other spec-lint-and-approve test in the repo
uses plain `node:test`, so this matches the existing pattern. The two exact
message strings, the row table, and the setup shape all come from the delta
spec.

## Missing context

The task said the new test should prove the scenarios via the traceability
`scenario` helper convention, but did not say what to do when the capability's
living spec has a pre-existing duplicate scenario name that makes
`lookupScenario` throw. I used plain tests, as the rest of the lint suite does.

## Outside scope

The living `spec-lint-and-approve` spec has two scenarios named "Python-only
repository". That is a pre-existing condition; I left it alone, as living specs
are never edited by an executor.
