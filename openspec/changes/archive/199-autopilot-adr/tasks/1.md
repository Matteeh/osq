## ADR text

```markdown
---
status: accepted
applies_to: [watcher-and-harness, cli-foundation, status-inspection, version-control]
rule: With autopilot on, a human approves the queue once; osq plans, approves, runs and lands each approved item in order and stops when recovery runs out.
checks:
  - tests/autopilot-adr.test.ts
---
# 021. Autopilot

Date: 2026-10-16

## Status

Accepted

## Context

A human today taps at least twice for every queue item: approve after the
plan, land after the archive. Between them the change runs by itself, and
ADR 018 and ADR 019 already let a planner run headless, for a run steering
trigger or on a tap. A human still approves every plan, and ADR 003 lets osq
write the default branch only through a command the human runs.

The next target is a fresh repository rebuilt from an exported queue. A human
and a planner shape the whole queue together, which is where the steering
happens, and from then on the build should run from the first item to the
last with nobody watching. Each tap in between adds no judgement the queue
session did not already give, and each one leaves the build waiting for
someone to notice.

Three accepted decisions stand in the way. ADR 006 rejects headless planning
for new changes and has the human tap every decision. ADR 018 rejects
planning queue items automatically, and its steering planner waits for a
human approve. ADR 003 writes the default branch only through a command the
human runs.

## Decision

1. **Off by default, per project.** A project turns it on with
   `autopilot.enabled` in its `osq.config.ts`. Without it, every queue item
   waits for `osq plan`, `osq approve` and `osq land` as before.
2. **The queue approval is the human gate.** The human plans the queue in a
   planner session and then runs `osq queue approve`. It records who approved
   and when, and the hash of every item's text, in one file only that command
   writes. An item whose text no longer matches its recorded hash, or that
   has none, is not approved: autopilot stops before it, and the next
   `osq queue approve` covers it. Editing the queue after approval never
   changes what runs unseen.
3. **One change at a time, in queue order.** With no active change, autopilot
   takes the first approved item that has no change yet and whose
   `Depends on` items have landed. Parallel changes are out of scope.
4. **The planner of ADR 019.** Autopilot plans an item as `osq plan <id> --run`
   does under ADR 019: the same prompt, the agent role's environment from
   ADR 007, a scratch worktree for a change folder in the checkout, and the
   same outcomes. Only `ready` goes on; `unchanged`, `lint_red`, `failed` and
   `timed_out` stop the queue.
5. **osq approves through `osq approve`.** A `ready` plan is approved through
   the same code as `osq approve`, with every gate it runs, and the approval
   records that autopilot gave it under the queue approval. The planner never
   approves. Autopilot never passes an override flag such as `--ignore-dirty`
   or `--base-ok`.
6. **Every gate stays.** Lint, the approve gates, each task's `verify`, the
   change `verify`, the scope, test and dependency gates, the archive and
   land `check`, and the validator all run as they do without autopilot. The
   validator still never stops a change (ADR 010). Autopilot has no path
   around a gate, and a gate that fails acts as it would with a human there.
7. **osq lands through `osq land`.** After archive, autopilot lands the change
   through the same code as `osq land`, `vcs.afterLand` included, and then
   takes the next item. A land that stops, on a conflict, a red check or
   anything else, stops the queue.
8. **The recovery ladder.** A halted change first gets the automatic retries
   `gates.autoRetries` allows, as today. A run steering trigger then gets the
   steering planner of ADR 018, as if `autoSteer.enabled` were on, and
   autopilot approves its `ready` revision as in decision 5. That is one
   round; a change gets at most `autopilot.maxSteers` rounds, 2 by default.
   A default-branch trigger, a steering outcome other than `ready`, or spent
   rounds stop the queue. A usage-limit pause pauses the queue and resumes
   it; it is not a failure.
9. **A stop asks one thing.** A stop writes one record naming the change,
   the trigger, its evidence and the one command that resumes the queue.
   The inbox, `osq status` and the dashboard show it, and nothing moves
   until a human acts.
10. **A human can always step in.** Turning autopilot off, or running any
    command on the active change, leaves the queue where it is. All of
    autopilot's state is in files, so the watcher picks it up again after a
    restart, including the restart ADR 012 makes after a land rebuilds osq.

## Consequences for ADR 003, ADR 006 and ADR 018

- ADR 003's rule stands as written. With autopilot on, `osq queue approve` is
  the command the human runs under which osq lands each approved item, and
  nothing reaches the default branch without that human decision. Decision 7's
  landing gains autopilot as a caller of the same code. Without autopilot,
  nothing changes.
- ADR 006 decision 2 still holds: the queue session is the steering, and
  `osq queue approve` is one tap standing for every approve and land tap of
  the items it covers. Its rejection of headless planning for new changes
  lifts for approved queue items with autopilot on. Decision 5's triggers
  stand; autopilot answers them first with the recovery ladder and asks the
  human when it runs out. Decision 4 is untouched: autopilot removes taps,
  never gates.
- ADR 018 keeps run triggers only, one run per trigger key and its outcome
  record. With autopilot on, decision 8 changes: a `ready` revision is
  approved by autopilot, at most `autopilot.maxSteers` times per change, and
  a human approves anything after that. Its rejection of planning queue items
  automatically lifts for approved items with autopilot on.
- ADR 019 is reused, not changed: autopilot's planner is its planner.

## Consequences

- A queue runs with nobody watching, one change at a time, and costs one
  planner run per item plus any steering rounds.
- The quality of an unwatched build rests on the gates alone. A weak `verify`
  that a human would have caught at approval now runs.
- A stopped queue waits until someone reads the inbox. Notifications beyond
  the inbox are not decided here.

## Rejected

- **A human approve and land tap for every item.** That is osq without
  autopilot, and it stays the default.
- **Skipping a gate to keep the queue moving.** A gate blocks or is removed
  (ADR 006); autopilot changes who taps, not what is checked.
- **A queue approval without item hashes.** An item edited after approval
  would run unseen.
- **Unlimited steering rounds.** A plan that keeps missing needs a human, and
  each round costs a planner run.
- **Steering default-branch triggers.** ADR 018 leaves them to a human, and
  autopilot does too.
- **Running changes in parallel.** One change at a time keeps landing and the
  recovery ladder simple; parallel changes are a later decision.
- **On by default.** A project chooses to build unwatched.
```
