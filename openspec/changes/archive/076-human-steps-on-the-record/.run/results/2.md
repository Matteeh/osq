## Changed

- Added `src/core/lifecycle/verification-record.ts`: exports the `check_ran`
  data type (`command`, `exitCode`, `duration`, `timedOut`, `output`) and the
  `verification_recorded` data type (`outcome`, `note`), plus
  `recordVerification(projectRoot, id, outcome, note, config)` and
  `runCheck(projectRoot, id, config)`. Both resolve an archived change with
  `resolveSpecFolder` from `src/core/status/show.ts`, read its requirement with
  `readVerification`, refuse a non-archived change and one with no recorded
  requirement, and append straight to the archived folder's
  `.run/events/change.jsonl` the way `appendRejectedEvent` does. `runCheck` runs
  the recorded command through `runVerificationCommand` with
  `config.timeouts.verifyTimeoutSeconds` from the project root.
- Changed `src/watcher/archiver.ts`: `archiveSpecFolder` now calls a new
  `readArchivedVerification` helper before the move, which reads the proposal
  with `parseSpecMdFromFolder`, `parseHumanSteps`, and `readCheckCommand`; when
  after-landing steps or a check exist, the `archived` event data is typed
  `ArchivedEventData & { verification?: VerificationRequirement }` and carries
  `verification: { afterLanding, check }`, otherwise only `archivePath` as
  before. `src/harness/types.ts` is unchanged.
- Added `src/cli/check.ts`: `checkCommand` prints the command, exit code,
  duration, output, and `Next: <formatNextStep>`, exits 1 after a failing or
  timed-out check, and exits 1 writing nothing on refusal. It also exports
  `registerVerificationCommands` for both new commands.
- Added `src/cli/verified.ts`: `verifiedCommand` requires exactly one of
  `--passed`/`--failed`, appends one outcome through `recordVerification`, and
  prints the change's next step; every refusal writes nothing.
- Changed `src/cli/index.ts` to import and call `registerVerificationCommands`,
  registering `check <id>` and `verified <id>` with `--passed`, `--failed`, and
  `--note <text>`.
- Added `tests/verification-record.test.ts` with 20 tests: it archives changes
  with `archiveSpecFolder` against a temp project and covers every scenario of
  "Archived verification requirement", "Human verification events", "Check
  command", and "Verified command", including that each refusal appends nothing.
  The check command is a local `node check.cjs` in the test's own temp project;
  the CLI tests stub `process.exit` as `tests/approve-confirm.test.ts` does.

## Deviated

- `osq check` and `osq verified` are registered through one
  `registerVerificationCommands(program)` helper exported by `src/cli/check.ts`
  instead of two inline blocks in `src/cli/index.ts`. Inline registration and
  the two imports pushed `index.ts` to 251 measured lines against its 250-line
  budget, so the helper removes the duplication and one blank line was dropped
  between `parseRejectReason` and `createProgram` to land at exactly 250.
- `runCheck` additionally refuses an archived change whose recorded requirement
  has a null `check` even though it requires verification, because the CLI spec
  says `osq check` refuses such a change; `recordVerification` refuses only when
  no verification is required, so a passed change can be recorded again and
  appended to.
