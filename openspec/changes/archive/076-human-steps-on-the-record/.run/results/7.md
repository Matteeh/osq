## Changed

- `src/core/status/show.ts`:
  - `SpecDetails` gains optional `next?: NextStep` and `verification?:
    VerificationHistory`, plus the `VerificationCheckRow`,
    `VerificationOutcomeRow`, and `VerificationHistory` types.
  - `getSpecDetails` now attaches the result of `withNextStep` to the built
    details: `readNextStep` for active and archived folders, left absent for
    rejected ones. For an archived folder whose `readVerification` says a
    requirement is recorded, it also attaches `buildVerificationHistory`, which
    projects the already-parsed change-level `check_ran` and
    `verification_recorded` events (time, command, exit code; time, outcome,
    note) from `details.timeline`.
  - `formatSpecDetails` prints `Next: <formatNextStep>` immediately after the
    `Status:` line when `next` is set, then a `Verification:` section via
    `formatVerificationHistory` when `verification` is set.
- Added `tests/show-next-step.test.ts` covering an archived change that
  recorded `passed` (`Next: landed` plus the outcome row), a failed outcome
  (`verification pending (failed) — osq verified 012 --passed|--failed`), a
  `check_ran` row with the command moving from `osq check` to `osq verified`
  after the check runs, an active unplanned change (`Next: unplanned — osq
  lint 014`), a rejected change with no `next`, and `--json` carrying
  `next: { state, command, detail }`. Each archived change's
  `.run/events/change.jsonl` is written by the test.

## Deviated

- The acceptance says the history is "filled by `getSpecDetails`". I attached
  `next`/`verification` in `getSpecDetails` only, not in the shared
  `buildSpecDetails`, so `getSpecDetailsFromFolder` (used by web inspection)
  keeps its existing projection and is unaffected.
- The status-inspection delta does not fix a byte format for the `Verification:`
  section, so I chose one line per event naming the event type:
  `  check_ran <time>: <command> (exit <n>)` and
  `  verification_recorded <time>: <outcome> (note: <note|none>)`, with
  `unavailable` for missing values. It carries every field the requirement
  names.
- `SpecDetails` also gains an optional `verification` field beyond the named
  `next`, since `formatSpecDetails` needs the rows to render the section.
