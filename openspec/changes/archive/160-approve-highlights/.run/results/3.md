## Changed

- Added `src/core/foundation/config-notices.ts` with `NoticesConfig`,
  `DEFAULT_NOTICES_CONFIG` (`{ maxShown: 5, maxTasks: 6, maxResolvedFiles: 15,
  rulePaths: [] }`) and `validateNoticesConfig`, modelled on `config-watch.ts`.
  It throws `notices configuration must be an object`,
  `notices.<key> must be a positive integer`, and
  `notices.rulePaths must be a list of scope patterns`.
- `src/core/foundation/config.ts`: merged the two `config-confinement.js`
  imports into one; added the `config-notices.js` import; added
  `readonly notices?: NoticesConfig` to `OsqConfig`, `notices:
  DEFAULT_NOTICES_CONFIG` to `DEFAULT_CONFIG`, and
  `notices: validateNoticesConfig(config.notices)` to `defineConfig`; wrote
  the `paths` and `timeouts` merges on one line each; collapsed the
  `defineConfig` destructuring to one line and let `watch` pass through
  `restConfig` (validated separately) so the file is 247 lines.
- `src/core/foundation/config-user.ts`: added `notices` to the `Omit` list and
  `readonly notices?: Partial<NoticesConfig>`.
- `osq.config.ts`: added `notices: { rulePaths: ["src/harness/prompt.ts",
  "src/core/foundation/init-blocks.ts"] }`, changing nothing else.
- Added `src/core/spec/plan-ready.ts`: `PlanReadyRecord`, `readPlanReady`
  (file order, skipping blank and malformed lines),
  `appendPlanReady` (writes the exact record line, creating `.run/`), and
  `countPlanRevisions`.
- Added `src/core/spec/notices.ts`: the notice types (`NoticeSeverity`,
  `ApprovalNoticeId`, `ApprovalNotice`, `ApprovalNotices`, `RecordedNotice`),
  plus `buildApprovalNotices`, `formatApprovalNotices` and `recordNotices`,
  reading `config.notices ?? DEFAULT_NOTICES_CONFIG` and ordering/folding per
  the delta.
- Added `src/core/spec/notice-rules.ts`: the twelve rules and
  `collectApprovalNotices`, re-reading tasks (`parseTaskMd` + `resolveScope`),
  delta specs (`parseDelta`), the proposal body, and `plan.jsonl`; the digest
  supplies tasks' `scopeFiles`/`testsModify`/`existingTests`, capability
  `removed`/`creates`, and the `adr_departure` flags.
- Added `src/core/spec/notice-readers.ts`: the folder readers the rules need
  (`readTaskFacts`, `readProposalBody`, `readChangeDeltas`).
- Added `tests/notices-rules.test.ts`: `createProject`/`createChange` fixtures
  covering each rule row on its own (thirteen cases, the `plan_revised` one
  writing its two records with `appendPlanReady`), the plain change, the
  covered-requirement case, the seven-notice ordering/folding case, the
  grey-only "Nothing unusual" case, and the revision count.
- Added `tests/notices-config.test.ts`: the default block, the partial block,
  the four invalid-block rows, and `loadConfig` on this repository holding the
  two rule paths.

`node --import tsx --import ./tests/git-test-env.ts --test
tests/notices-rules.test.ts tests/notices-config.test.ts` passes (27 tests).
`pnpm verify` (the proposal verify) passes: both typechecks, the build, every
CLI and UI test, and lint.

## Deviated

- The task said to put the rules in `src/core/spec/notice-rules.ts` if
  `notices.ts` would pass 250 lines. `notice-rules.ts` with its readers was
  still 266 lines, so I moved only the folder-reading helpers
  (`readTaskFacts`, `readProposalBody`, `readChangeDeltas` and their private
  helpers) into a new `src/core/spec/notice-readers.ts` (matches the task's
  `notice*.ts` scope). The rules themselves stay in `notice-rules.ts`.
- To keep `config.ts` at 247 lines I also collapsed the `defineConfig`
  destructuring to one line and let `watch` flow through `restConfig` with a
  separate validated override, beyond the two savings the task named. Behavior
  is unchanged: `watch` is still `validateWatchConfig(config.watch)`.
- `RecordedNotice` carries `id`/`severity`/`folded` as the ports specify, so
  `countPlanRevisions` and the `plan_revised` rule work without task 4.

## Outside scope

- `src/core/report/planning-records.ts` already skips `plan_ready` lines
  because `parsePlanRecord` returns null for any record without a
  `sessionId`. No change was needed there, and readers of `plan_started` and
  `plan_exited` already meet the requirement.
