## Acceptance

- [ ] `ApprovalDigest` gains `readonly notices?: ApprovalNoticeRecord`, documented as set only by `confirmApproval`, where `ApprovalNoticeRecord` is `{ readonly items: readonly RecordedNotice[]; readonly opened: readonly string[] | null }`, declared in `digest.ts` with `RecordedNotice` imported as a type. `buildApprovalDigest` never sets it. `digest.ts` stays at or under 250 lines.
- [ ] `ApprovalReviewOptions` gains `openedNotices?: readonly string[]`, and its `review` port becomes `(digest, notices: ApprovalNotices) => Promise<ApprovalReview>`. `confirmApproval` builds the notices with `buildApprovalNotices`, refuses an unopened red notice before calling `review` as "Notices at approval" in the spec-lint-and-approve delta says, and returns the digest with `notices` set from `recordNotices` and the filtered `opened`.
- [ ] `writeApprovalSeal` passes `digest.notices` to `buildManifest`, which records it as the manifest's `notices` as "Approval notices in the manifest" in the watcher-and-harness delta says. `ManifestData` gains `notices?: ApprovalNoticeRecord`; a planning-only manifest has none. `manifest.ts` stays at or under 250 lines.
- [ ] `approveCommand` takes `openedNotices` in its options, passes it to `approveSpec`, and its review prints `formatApprovalNotices(notices)`, one line each, before the digest, with and without `--confirm`. No CLI flag is added.
- [ ] New `tests/approve-notices.test.ts` covers every scenario of "Notices at approval" and "Approval notices in the manifest" through `approveCommand` and `approveSpec` on temporary projects without version control, as `tests/show-digest.test.ts` approves, including the refusal writing neither `.run/approved` nor a manifest.
- [ ] Every existing test passes unchanged.

## Details

Every approval path calls `confirmApproval` with the options `approveSpec`
received and hands its `digest` to `writeApprovalSeal`, so the new option and
field reach in-place, worktree, stacked, steering and default-branch approvals
without touching those files. `osq serve`'s runner is wired in task 6.

The refusal is a plain `Error`; `approveCommand` already turns it into
`Error approving <id>:` with the next step.
