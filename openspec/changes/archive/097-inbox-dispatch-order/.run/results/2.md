# Task 2 — Dispatch order

## Changed

- Added `src/core/status/dispatch-order.ts`. `orderDispatchItems(projectRoot,
  config, dispatch)` reads every active change in every tree with
  `listChanges`, reads each one's `depends_on` with `parseSpecMdFromFolder`,
  and adds `weight` and `reason` to each item.
  - Weight is one plus the number of active changes whose `depends_on` reaches
    the item's change directly or through other active changes. Ids match
    folders with `matchesFolder`; a per-candidate visited set makes a cycle
    terminate and count each change once.
  - Sort: with `watcherIdle`, `approval` and `halt` first; then higher weight;
    then lower numeric change id; then change-level before task items, then
    lower task number.
  - Reason parts join with `; `: `watcher idle; this gives it work` when the
    idle rule puts the item first, and `holds up <n> change`/`changes` for
    weight above one; alone, `in change order`.
  - Exported the `OrderedDispatchItem` type (`DispatchItem` plus `weight` and
    `reason`).
- Added `tests/dispatch-order.test.ts` covering every "Dispatch order"
  scenario by reading real items with `readDispatchItems` from temporary
  projects: transitive weight, idle watcher, equal items, and a dependency
  cycle. It also builds a stacked approval tree (`vcs.enabled`) so an active
  change in another tree counts toward the weight, and asserts two calls give
  the same order.

## Deviated

- The delta fixes `orderDispatchItems(projectRoot, config, dispatch)`, so
  `config` is required (a defaulted `config` cannot precede the required
  `dispatch`). Task 4 passes it explicitly.
- The delta names no return type; I exported `OrderedDispatchItem`.
