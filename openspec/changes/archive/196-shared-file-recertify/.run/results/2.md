## Changed

- `src/core/status/steering.ts`: `taskTrigger` now parses the active regressed
  marker's frontmatter and returns no trigger when its `reason` is
  `scope_regression` and its `verification_passed` is `true`, so a passing
  scope regression is no longer a `regression` steering trigger. Every other
  regressed marker, a `scope_regression` with `verification_passed: false`
  among them, still returns the `regression` trigger. Added the two
  `@scenario status-inspection:` lines to `deriveSteering`'s doc comment.
- `tests/scope-regression-retry.test.ts`: new test that builds approved change
  `007-pricing` with task 3's `.run/regressed/3.md` written by
  `buildScopeRegressionMarker`, and proves "Passing scope regression" and
  "Failing scope regression" through `deriveSteering`/`deriveSpecState`, and
  "Passing scope regression next step" through `readNextStep`, `readInbox`
  (the `osq --json` inbox) and `readDispatchItems`.

`next-step.ts`, `inbox.ts` and `dispatch-items.ts` were left alone: a
regressed task without steering already yields `osq retry <id> <n>`.

Task verify (`node --import tsx ... tests/scope-regression-retry.test.ts
tests/steering-triggers.test.ts`) passes: 16 tests, `tests/steering-triggers.test.ts`
unchanged. Proposal verify (`pnpm verify`) passes.
