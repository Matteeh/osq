## Changed

- `src/core/spec/stack-cut.ts`: `decideStackCut` now distinguishes declared
  `.run/stacked-on` lines from overlap lines through `parseStackedOn`'s
  `overlap` field. Declared lines keep their exact previous behavior
  (`dependency_changed` halts with the same details, and `dependency_diverged`
  is unchanged for declared-only stacks). An overlap line whose change reads
  `unapproved`, or `approved` or `archived` with another hash, is dropped
  instead of halting. `resolveArchivedBase` now requires the chosen archived
  branch to hold every other archived dependency's archive and every landed
  overlap's archive, and waits (instead of halting) when no branch holds them
  and any remaining line is an overlap line; the "nothing to hold" case now
  also covers a stack whose lines were all dropped, which cuts from the
  default branch. Tagged `@scenario watcher-and-harness: Overlapping changes
  approved at once`, `@scenario watcher-and-harness: Overlap lines in the
  cut`, and `@adr 003`.
- `tests/stack-overlap-cut.test.ts` (new): proves "Overlapping changes
  approved at once" end to end through `approveSpec` + `runWatcherOnce` with
  an adapter that edits one scoped file per task, asserting `osq/002-b`'s
  first commit is `osq: 002 approved` whose parent is `osq/001-a`'s
  `osq: 001 archived` commit, that `osq/002-b` ends with `osq: 002 archived`
  with no sync commit, and that the stacked approval directory is gone. It
  also proves every row of "Overlap lines in the cut" through
  `decideStackCut` on a stacked `003-c` copy whose `.run/stacked-on` the test
  writes, with the dependency states built through real approvals, branch
  archives, a branch rejection, a re-approval hash change, and squash-merges
  onto `main`.

## Deviated

- The "Overlapping changes approved at once" end-to-end test uses the default
  `gates.autoRetries` (1) instead of the 0 that the stack-run tests use. A
  stacked overlap change has no `depends_on` (the scenario declares
  `depends_on: []`), so its derived state is `pending` and the watcher's
  change loop runs its task once from the stacked copy before the cut
  happens. That wasted attempt dies and is copied into the worktree at the
  cut; the default automatic retry then runs it in the worktree, and the
  scenario's THEN (first commit `osq: 002 approved` over `osq: 001 archived`,
  ending archived, no sync, stacked directory gone) holds. The decision rows
  of "Overlap lines in the cut" are proven through `decideStackCut`, which is
  where this task's scope lies.

## Outside scope

- The watcher change loop (`src/watcher/loop.ts`) still treats an active
  change in a stacked tree as runnable and will spawn its task from the
  stacked copy once before `runStackedChanges` cuts it, because a stacked
  overlap change has no `depends_on` entry to make its derived state
  `blocked`. With `gates.autoRetries` at 0, that wasted attempt would leave
  the cut worktree dead and need a human retry. The natural fix is for the
  loop to skip any change whose tree has a `stackedFolder`, which is outside
  this task's scope.
