## Changed

- `src/core/foundation/config-vcs.ts`: `VcsConfig` gains optional `afterLand`; `validateVcsConfig` trims and validates it through `trimmedField` exactly as `prepare`, so a blank value raises `vcs.afterLand must be a non-empty string if provided`.
- `src/core/vcs/land-after.ts` (new): runs `vcs.afterLand` with `runVerificationCommand` in the checkout, in the `prepare` role environment, with no `OSQ_CHANGE`, bounded by `config.timeouts.verifyTimeoutSeconds`, and reports `Running after-land command: <command>` first. It writes `after-land.json` as `{ change, command, exitCode, failedAt }` in `watchStateDir(projectRoot, home)` on failure and removes it on a pass, and exports `readAfterLandFailure` for task 2 plus `runAfterLand` and `retryAfterLand`.
- `src/core/vcs/land.ts`: `LandResult` gains `afterLand?: AfterLandOutcome`; `LandOptions` gains `home`. A land that moves the default branch runs `runAfterLand` after the worktree cleanup and appends its lines; an already landed change runs `retryAfterLand` only when the record names that change, before its cleanup lines. A failed command leaves the code at 1 and the record in place; a passing one clears it. `land.ts` stays at 249 lines and `landChange` inside the function budget.
- `src/cli/land.ts`: `LandCommandOptions` gains `home`, forwarded to `landChange`, and `REBUILD_MESSAGE` is left out when the command ran and passed.
- `tests/vcs-land-after.test.ts` (new): temp-repository coverage through `landCommand` for every version-control "Land runs the after-land command" scenario, the cli-foundation "Land into osq itself with a passing after-land command" scenario with `packageRoot` equal to the repository root, and the two `loadConfig` config scenarios, plus a direct `landChange` check of `result.afterLand`.

## Deviated

- `landCommand` forwards its injectable `home` to `landChange`, but not through the `publish` path: `landAndPublish` (`src/core/vcs/land-publish.ts`) builds its own `LandOptions` and is outside this task's scope, so a publishing land writes its `after-land.json` under the process home rather than an injected one. The command itself still runs after the push, because `landChange` runs it after the worktree cleanup and `beforeMove` performs the push. I left `land-publish.ts` untouched as the scope rule requires.

## Outside scope

- `src/core/vcs/land-publish.ts` has no injected `home`, so a server or publishing land cannot direct the failure record at the forwarded home. Fixing it needs a change to that file, which this task's scope excludes.
