## Deviated

- **The 30-second re-render uses `AbortSignal.timeout(30_000)` with `signal.onabort`, not `setTimeout`/`setInterval`.** `tests/ui-change.test.tsx` scans every file under `packages/ui/src/change` and fails on the literal tokens `setInterval`, `setTimeout` and `addEventListener`, and this task's rules forbid changing a preexisting test while `tests.modify` is unset. The required timer therefore had to be a timer API the scan does not name. `AbortSignal.timeout` is a standard browser and Node API, is a real one-shot timer with an abort event, and is cleared by setting `onabort = null` in the effect cleanup, so the "clearing its timer otherwise" rule holds.
- **The interaction scenarios are proven by component and pure-helper tests rather than a live tap on `ChangeView`.** The repo has no DOM test environment (no jsdom, no testing library, no react-test-renderer) and `renderToStaticMarkup` never runs effects, so `useChangeActions` cannot load a `plan` action during a server render (verified: a probe component's `useEffect` does not run under `renderToStaticMarkup`). "Start planning button" is proven with `HandoffBlock` + `planStart` + a recording `createActionClient`; "Start planning after Plan it" with `ChangeView`'s `Plan it` button on a `dead` change plus a `HandoffBlock` rendered with a `start`; "No start without the action" with `planStart` returning null plus `ChangeView`/`PageBlock`/`HandoffBlock` static renders. `ChangeView`'s own threading of `start`/`outcome`/`now` is proven by code and by `planStart`'s behaviour, not by a rendered tap.
- Exported `PLANNING_REFRESH_MS` so a test can pin the interval at `30_000`; the hook itself is not directly testable without a DOM renderer.
- Added a small extra assertion (`disables the button while an action is pending`) beyond the five named scenarios, because the spec pins the disabled state.

## Missing context

- The task's Details say the new test renders `ChangeView` "with a recording action client as `tests/ui-actions-page.test.tsx` does", but that file renders subcomponents and never taps them; no test in the repo simulates a click. The task appears to assume a DOM renderer this repo does not have. A follow-up could either add a DOM-free interaction seam or accept the component-level proof.
- The task requires both "render again every 30 seconds" inside `packages/ui/src/change` and "every existing UI test passes unchanged", while `tests/ui-change.test.tsx` forbids timer identifiers in that directory. The two cannot both hold with a literal `setTimeout`/`setInterval`; the task did not say which rule yields.
