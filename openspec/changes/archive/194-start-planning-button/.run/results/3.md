## Changed

- `src/core/status/next-step.ts`: `NextStepState` gained `planning`, and `readActiveNextStep` now returns `{ state: 'planning', command: 'osq show <id>', detail: 'since <formatPauseUntil(since)>' }` from `readLivePlanner(state)` before every other active-change rule, approved or not. `formatNextStep` renders it through its existing path. Doc comments gained the `Planning format`, `Steering while planning` and `Planner that stopped` scenarios and `@adr 019`.
- New `src/core/status/plan-run-eligible.ts`: `canStartPlanner(next, location, config)`, true only for an `active` location, `vcs.enabled`, and a next step of `unplanned`, `ready-for-approval`, or `dead` with detail `needs steering`. It reads only its arguments.
- `src/core/web/web-data-next.ts`: new exported `WebPlanRun` `{ outcome, startedAt, detail }`; `WebChangeNext` gained `planRun`, derived for an active change from `currentPlanRun(state)` with `startedAt` the record's `at` while `running` else null, and null for archived/rejected/underivable changes. Doc comment gained the three document scenarios and `@adr 019`.
- `src/core/web/web-data-types.ts`: `WebChange` gained the optional `planRun?: WebPlanRun | null`.
- `src/core/web/web-data-change.ts`: `getWebChange` copies `planRun: next.planRun` onto the document beside `autoSteer`; doc comment gained the three document scenarios and `@adr 019`.
- `packages/ui/src/change/page-model.ts`: `changePage` handles `planning` as `Planning` / `Planner running` / null buttons; new `planningLine(change, now)` renders `Planning on server · <elapsed>` reusing the `elapsedText` `progressLine` uses (clamped at 0, `unavailable` when `planRun` or `startedAt` is missing); new `planRunLine(change)` renders the outcome line for `unchanged`/`lint_red`/`timed_out`/`failed` and null for `running`/`ready`. Kept to 247 lines.
- New `tests/plan-run-status.test.ts`: seven plain `node:test` cases proving `Planning format` (through `showCommand` and `statusCommand` with captured output), `Steering while planning`, `Planner that stopped`, `Who may start a planner` (the whole table), `Running planner in the document`, `Finished planner in the document` and `No planner run`.
- `tests/ui-page-model.test.tsx`: added a `planning` case to `Page per state` and new `Planning line` and `Planner run line` suites with the documents and times from the scenarios. Existing cases are untouched.

Task verify: 7 pass. Proposal verify (`pnpm verify`): exit 0, 223 tests, both typechecks, build and lint.

## Deviated

- The new tests use plain `node:test` `describe`/`it`, matching `tests/usage-pause-next-step.test.ts` and task 2's tests in this change, rather than the `scenario(...)` helper. osq opts only its `traceability` capability into traceability, so these status-inspection and web-inspection scenarios are not under the helper's scope. The exported functions still carry the required `@scenario`/`@adr` tags.
- `canStartPlanner` types `location` as `WebLocation` imported from `src/core/web/web-data-types.ts`, the type `resolveChangeFolder` returns to the task 4/5 callers, rather than a fresh union. `src/core/status` already imports from `src/core/web` (`dispatch-watch.ts`), and the import is type-only, so no runtime edge is added.
