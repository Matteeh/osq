## Changed

- `src/core/status/validator-failing.ts` (new): `ValidatorFailing` and `readValidatorFailing(projectRoot, config)`. It reads the `validator_ran` events of every archived change `listChanges(projectRoot, config, ['archived'])` finds through task 3's `readValidatorRuns` (not edited), leaves out `not_run` runs, orders the rest by event timestamp (stable), and returns `{ change, outcome, runs, error }` when the latest run's outcome is `failed`, `timed_out`, or `unreadable`: `runs` counts the latest runs in a row with one of those outcomes, and `error` is the first non-blank line of the latest run's `output`, trimmed, or its outcome when the output is absent or blank. Otherwise it returns null, so one `validated` run clears the line. It writes nothing.
- `src/core/status/inbox.ts`: `NeedsYouKind` gains `validator-failing` and `NeedsYouItem` gains optional `validatorFailing: { outcome, runs, error }`. Still 246 lines, under the 250-line budget (the two long lines carry the existing biome-ignore format comments).
- `src/core/status/inbox-projection.ts`: new `validatorFailingItem` builds the item `{ kind: 'validator-failing', change: { id, title }, task: null, command: 'osq show <id>', validatorFailing }` with the title from the change's proposal or else its folder name; `readInbox` appends it next to the after-land item and sorts the needs-you group by id.
- `src/core/status/inbox-text.ts`: `needsYouLine` renders a validator-failing item as `  <id>: <title> — validator <outcome> <runs>× in a row: <error> — osq show <id>`; every other line is untouched.
- `src/cli/status.ts`: `statusCommand` prints `Validator <outcome> <runs>× in a row, last on <id>: <error> — osq show <id>` after the watcher line, the `Log:` line, and the after-land line, nothing when `readValidatorFailing` is null.
- `packages/ui/src/home/labels.ts`: `NEEDS_YOU_LABELS` gains `validator-failing: 'validator failing'`.
- `tests/inbox-validator-failing.test.ts` (new): proves all four rows of "Validator failing" (failed/failed in time order, validated/timed_out, failed/not_run, failed/validated clears), "No validator runs", and "Validator failing label" through `readValidatorFailing`, `readInbox`, `formatInboxText`, and `statusCommand` with an injected home and captured writers over temporary archives, as `tests/inbox-after-land.test.ts` does.

All changed/added exported functions carry `@scenario status-inspection:` / `@scenario web-inspection:` lines for the scenarios they serve and `@adr 010`.

## Deviated

- The validator-failing item's title looks the proposal up under the first change tree's archive directory, exactly as the `after-land-failed` item does. A failing change archived in an osq worktree's archive (not the checkout's) therefore falls back to its folder name even when its proposal carries a title. The scenario only exercises the checkout archive, and the acceptance line names the after-land item as the model to copy.
