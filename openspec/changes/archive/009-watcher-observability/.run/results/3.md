# Task 3 result — runner lifecycle logging

## Changed

- `src/harness/process.ts`
  - `SpawnProcessResult` gained optional `pid?: number` and `elapsedMs?: number`.
  - `spawnWithTimeout` records `startTime = Date.now()` before spawning and `child.pid` from `spawn()`, then enriches every resolved result in `finish()` with `pid` and `elapsedMs: Date.now() - startTime` (both success/error/close paths).
- `src/harness/types.ts`
  - `SpawnResult` gained optional `pid?: number` and `elapsedMs?: number`.
- `src/watcher/runner.ts`
  - Added `logger?: Logger` as the sixth parameter of `runTask` (imports `Logger` type).
  - Added private `recordLifecycleEvent(specFolderPath, taskNumber, event, summary, logger)` that appends the harness event and calls `logger?.info(summary)` in one code path (satisfies the spec invariant).
  - After `adapter.spawn` returns, `runTask` computes `elapsedSeconds` from `spawnResult.elapsedMs ?? (Date.now() - spawnStartMs)` and records:
    - `started` event `{ pid, timeoutSeconds }` + `task N started (pid: <pid>, timeout: <T>s)`
    - `exited` event `{ exitCode, signal, timedOut, elapsedSeconds }` + `task N exited (code: <C>, elapsed: <E>s)`
- `tests/runner-lifecycle-logging.test.ts` (new)
  - Assert `spawnWithTimeout` captures the child's real pid (compares against the child's self-reported `process.pid`) and a non-negative `elapsedMs`.
  - Compile-time/type assertions for `pid`/`elapsedMs` on both result interfaces.
  - Stub adapter returning explicit `pid`/`elapsedMs`; intercepts `process.stderr.write` with `createLogger('normal')` to assert the `started` and `exited` summaries.
  - Asserts the matching `started`/`exited` entries in `.run/events/1.jsonl` carry `pid`, `timeoutSeconds`, `exitCode`, `elapsedSeconds`.
  - Asserts the log line and event record agree (same code path) and that omitting the logger emits no stderr but still appends both events.

## Deviated

- Lifecycle events are recorded **around** `adapter.spawn` (immediately after it resolves) rather than inside the adapter at the live spawn moment. The `runTask` signature in the task gives no way to observe `child.pid` before `spawn` resolves, so `started` is appended after the process has exited and its `timestamp` is backdated to `spawnStartMs`. The event content (pid, timeout, exit code, elapsed) is accurate.
- The built-in adapters (`agy.ts`, `opencode.ts`, `mock.ts`) are out of this task's scope and therefore still append their own `started`/`exited` events. A real `runTask` run will therefore persist duplicate lifecycle entries (`adapter started`, ..., `adapter exited`, `runner started`, `runner exited`, `verify_ran`). The new tests use a stub adapter that does not emit its own lifecycle events, so they isolate runner behavior.

## Drift against features/

- `features/watcher-and-harness.md` is intentionally untouched; feature docs only change when the watcher applies the approved spec `## Delta`. The new lifecycle logging is additive and not yet documented there.

## Missing context

- Out-of-scope integration gap: built-in adapters do not yet propagate `pid`/`elapsedMs` from `spawnWithTimeout` into their `SpawnResult`, so for real adapters the `started` log/event will show `pid: unknown` and `elapsedSeconds` falls back to runner wall-clock time. Propagating the fields means touching `src/harness/agy.ts`, `opencode.ts`, and `mock.ts`.
- The duplicate lifecycle events noted under Deviated could be removed by deleting the adapter-level `started`/`exited` appends once the runner owns them; that requires adapter edits outside this task's scope.
- Task 2 noted `startWatcher`/`runWatcherCycle` in `src/watcher/loop.ts` do not yet accept/forward a logger, so `runTask` currently only receives a logger when called directly. `loop.ts` is outside this task's scope.
