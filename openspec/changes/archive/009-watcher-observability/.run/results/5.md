# Task 5 result — opencode tool_use → tool event + verbose log

## Changed

- `src/harness/types.ts`
  - Added `'tool'` to `HarnessEventType`.
  - Added `ToolEventData { tool: string; summary: string }`.
  - Added optional `logger?: Logger` to `SpawnTaskOptions` so the adapter can forward the shared logger into the stdout parser.
- `src/harness/opencode.ts`
  - Imported `Logger` (type-only) from `../core/logger.js` and `ToolEventData` from `./types.js`.
  - Added `extractToolEventSummary(toolName, input)`:
    - `read|edit|write|glob` → target from `input.path`, `input.file`, `input.filepath`, `input.filePath`, `input.pattern`.
    - `bash` → `input.command`/`input.cmd` sliced to 60 chars.
    - other → 60 chars of `JSON.stringify(input)` (or `String(input)` for primitives).
  - Added `extractOpencodeToolEvent(event)`:
    - Recognizes top-level `type === 'tool_use'` and `part.type === 'tool-use'` (also `'tool_use'`).
    - Resolves tool name from `event.tool`/`event.name`/`part.tool`/`part.name`.
    - Resolves input from `event.input`/`event.parameters`/`part.input`/`part.parameters`/`part.state.input`/`part.state.parameters`.
    - Returns `null` for non-tool and malformed events (no tool name).
  - Added `recordToolEvent(...)`: the single shared handler path that appends `{ type: 'tool', timestamp, data: { tool, summary } }` to `.run/events/<n>.jsonl` and calls `logger?.verbose('[tool] <tool>: <summary>')`.
  - `processOpencodeStdoutLine` gained optional `logger?: Logger`; it checks `extractOpencodeToolEvent` first, records through `recordToolEvent`, and returns. `step_finish` handling is unchanged except it reuses the new `resolveEventTimestamp` helper.
  - `OpencodeEventStreamParser` constructor gained optional `logger` and forwards it on every line.
  - `OpencodeAdapter.spawn` passes `options.logger` into the parser.
- `tests/opencode-tool-events.test.ts` (new, the task verify command): 9 tests covering the `'tool'` event type/ToolEventData, summary extraction for file tools, bash truncation, generic JSON fallback, `tool_use`/`tool-use` recognition (top-level, nested, and `part.state.input`), event persistence + verbose stderr log from `processOpencodeStdoutLine`, normal-level suppression, parser forwarding, and an end-to-end adapter spawn with a fake binary emitting `tool_use`.

## Deviated

- Summary extraction also accepts camelCase `input.filePath` in addition to the listed `input.filepath`. Real OpenCode nests `filePath` under `part.state.input`; without it the acceptance line "extracts file path for read/edit/write/glob" would fail against live output.
- `extractOpencodeToolEvent` also accepts `part.type === 'tool_use'` (underscore) alongside the specified `'tool-use'` (hyphen), since both spellings appear in stream output.
- Added `logger?: Logger` to `SpawnTaskOptions` (types.ts is in scope) and threaded it through `OpencodeEventStreamParser`/`spawn`. Not in the task's signature list, but it is the only way the shared logger reaches the parser without touching `runner.ts`. No existing call site breaks (optional).
- Extracted the duplicated timestamp parsing in the `step_finish` branch into `resolveEventTimestamp`; behavior is identical (verified by existing token tests).

## Drift against features/

- `features/watcher-and-harness.md` is intentionally untouched; feature docs only change when the watcher applies the approved spec `## Delta`. The `tool` event and verbose tool logging are additive and undocumented until then.

## Missing context

- `src/watcher/runner.ts` does not pass `logger` into `adapter.spawn`, so a real `osq watch` run currently persists `tool` events but does **not** emit the verbose `[tool] ...` log line. `runner.ts` is outside this task's `scope`. Events are correct; only the live log path needs the one-line wiring (`logger` → `spawn options`).
- Antigravity (`src/harness/agy.ts`) still has no tool-event translation; the spec contract mentions Agy stream-json tool events, presumably a later task.
