## Changed

- Added `src/core/foundation/config-capabilities.ts`: `checkTraceabilityCapabilities(projectRoot, openspecRoot, capabilities)` returns early for `'all'` and for a project with no living capability spec, then throws `traceability.capabilities names unknown capability <name>; did you mean <nearest>?` for any name that has no living spec and is not listed in `creates` by an active (non-`archive`) change. It reuses `readLivingCapabilityNames` and `nearestCapability` from `src/core/spec/digest-capability.ts`, `readCreates` from `src/core/spec/capability-relations.ts`, and `parseFrontmatter` for each `proposal.md`. `unknownCapabilityMessage(name, living)` is exported so the suffix-omission branch has a direct test.
- `src/core/foundation/config.ts`: `loadConfig` now defines the config into `config`, runs `checkTraceabilityCapabilities` over `config.paths.openspecRoot` and `config.traceability?.capabilities ?? []` inside the existing try, and returns it. The existing catch still wraps any failure as a `ConfigLoadError` naming the config file.
- Added `tests/traceability-capability-names.test.ts`: every scenario of "Traceability capability names" through `loadConfig` on temporary projects holding an `osq.config.ts` (real name, misspelling with nearest name and exact `ConfigLoadError` message, a name an active change declares in `creates`, an archived change ignored, no living spec, `'all'`), plus a direct `unknownCapabilityMessage` test for the suffix left out when no living name exists.

## Deviated

- Exported `unknownCapabilityMessage` in addition to the check so the requirement's "suffix left out when there is none" clause is covered. Through `loadConfig` that branch is unreachable: the check only runs when a living spec exists, and `nearestCapability` then always returns a name.
