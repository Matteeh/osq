## Acceptance

- [ ] New `src/core/spec/capability-move.ts` exports `generateCapabilityMove(projectRoot, config, changeId, move)`, where `move` is `{ kind: 'rename', from, to }` or `{ kind: 'split', from, targets }`, and resolves to `{ folderPath, written, naming }`. It writes exactly what spec-lint-and-approve "Generated capability move" says: `specs/<old>/spec.md` first, then for each target `osq.yml`, when it gets one, and then `spec.md`, and `written` lists those paths in that order. It resolves the change with `findChange`, the way `resolveChange` in `web-remote-files.ts` does, and reads blocks with `parseCapabilitySpec`, the purpose with `extractPurposeSection`, and sidecars with `parseSidecar`. New sidecars come from `formatSidecar`, with `UNGROUPED` as the last fallback.
- [ ] New `src/core/spec/capability-move-map.ts` exports `readMoveMap(text)`, which parses the YAML map with `yaml` and returns the split targets in map order. It throws each refusal "Generated move map" lists that the text alone decides. The checks against the living spec are thrown by `generateCapabilityMove` before any file is written.
- [ ] New `src/core/spec/capability-move-proposal.ts` edits `proposal.md` as "Generated move proposal" says: frontmatter through `YAML.parseDocument`, so `depends_on: ["001"]` keeps its form, and the `## Generated` section, replaced when present. New `src/core/spec/capability-naming.ts` exports `findNamingFiles(projectRoot, config, capability)` for its second list. It never writes a file it scans.
- [ ] Every refusal throws an `Error` with the exact message, before anything is written. Running the generator again first removes the folders of the earlier `generated` field's `from` and `to`, as "Running it again" says.
- [ ] Each new file stays at or under 250 lines and each function at or under 80. The word "skipped" appears nowhere in them, comments included, because `tests/no-skipped-in-src.test.ts` bans it under `src/`.
- [ ] New `tests/capability-move.test.ts` builds temporary projects, each with an `openspec/specs/gadgets/` (`spec.md` and `osq.yml`), a living `pricing` spec, and an unapproved change `002` made the way `tests/capability-relations.test.ts` writes change folders. Through `generateCapabilityMove` and `readMoveMap` it checks every scenario of "Generated capability move", "Generated move map" and "Generated move proposal", including each table row. Expected values come from the THEN lines and tables, and the byte-for-byte scenario merges the written deltas with `mergeDelta`.
- [ ] Exported functions you add carry `@scenario spec-lint-and-approve: <scenario name>` lines for the scenarios they serve and `@adr 016`.
