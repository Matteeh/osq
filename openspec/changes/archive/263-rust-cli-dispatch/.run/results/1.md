## Changed

- `merge_ownership` in `crates/kernel/linter/src/gates/change.rs` now drops a capability's living globs when its delta REMOVES `Code ownership` and states no ADDED or MODIFIED replacement. ADDED and MODIFIED ownership still replace the living globs through `set_ownership`.
- `change_link_gates` also leaves an emptied capability out of the link graph, as archive would remove a capability with no requirements left. Without this, the proposal's own corpus run reports `rust-workspace owns no file` after its only requirement is removed. The capability's nodes and every edge touching it are filtered out.
- Added fixture changes `003-retire` (`keep` REMOVES `Code ownership`, `fresh` ADDS ownership over `crates/fresh/**`, `crates/keep/**` and `crates/split/**`) and `004-orphan` (`keep` REMOVES `Code ownership`), each removed requirement carrying `**Reason**` and `**Migration**`.
- Added `crates/kernel/linter/tests/link_gates_removed_ownership.rs` proving both new rust-linter scenarios, plus temporary-project tests for an emptied capability that is filtered while another capability stays scoped, a removal that leaves other requirements so the capability still exists, and a removed non-ownership requirement that must not drop ownership.

## Deviated

- The task's acceptance names only `merge_ownership`, but the proposal verify also failed with `openspec/specs/rust-workspace/spec.md: rust-workspace owns no file`. The change removes rust-workspace's only requirement, so archive removes the capability. I made `change_link_gates` model that by filtering the emptied capability out of the graph, which is the only in-scope way to let the proposal verify pass.
- Two extra tests beyond the two scenarios were added because the scenario fixtures empty `keep`, so graph filtering alone would hide whether `merge_ownership` actually removed its living globs. The extra temporary-project tests keep the removal logic and its mutation coverage honest.
