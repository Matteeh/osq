## Acceptance

- [ ] `src/watcher/lanes.ts` holds a `ChangeLanes` class: the in-process lanes keyed by change folder path. It starts a lane from a function, says whether a folder's lane runs and how many run, waits until fewer than a cap run (a cap under 1 counts as 1), waits until none run, hands over the outcomes of finished lanes (tasks run, specs archived, a `blocked_by_regression` entry), and keeps the first error a lane ended with for the watcher to rethrow. It never leaves a rejected promise unhandled.
- [ ] The lane body moves out of `runWatcherCycle` into `src/watcher/change-lane.ts`: the pre-dispatch scope audit with `formatScopeRegressionLine`, `runTask`, `runMutationCheck`, `commitWorktreeVerifiedTask`, the pause discard, `commitWorktreeDeadTask`, the halted line, and the archive after a pass. A lane logs its own error as `watcher error: <message>` like the cycle does, except a `StaleBuildError`, which it rethrows. The `archiveCompletedSpec` closure becomes an exported function in `src/watcher/archive-change.ts`, with `extractHumanSteps` and `readHumanSteps` beside it; `loop.ts` re-exports `extractHumanSteps` for `tests/cut-over.test.ts`, and the cycle's own archive of a `done` change calls the same function.
- [ ] `runWatcherCycle` gains an optional last parameter, the watcher's `ChangeLanes`. Without it the cycle makes its own and waits for every lane before it returns, so `runWatcherCycle` and `runWatcherOnce` return only after the tasks they started end, and the summary counts what the lanes did. With it, the cycle rethrows a kept lane error first, skips any change whose lane runs (still counting it as approved waiting), and does not wait at the end. The idle status prints only when no task ran and no lane runs.
- [ ] Before it starts a change's next task, the cycle waits for a free lane under `config.maxConcurrency`, then runs the stale check, the pause check and the first-task sync as today, logs the `picked up` line, and starts the lane. Changes are still visited in numeric order, so with `maxConcurrency: 1` tasks run in today's order. A change whose `tree.stackedFolder` is set starts no task; it waits for `runStackedChanges` to cut it. Today the cycle spawns a stacked copy's task in its stacked tree once its base finishes; that attempt goes away.
- [ ] `startWatcher` makes one `ChangeLanes` and passes it to every continuous cycle. Stopping waits for it: the SIGINT listener stays until every lane has finished, so a second SIGINT still exits with 130; the promise of a watcher with a signal resolves only once no cycle and no lane runs, including on the early returns after the first cycle and after `changeTrees`; and a `StaleBuildError`, a `BuildChangedError` included, waits for every lane to finish before `handleStaleBuild` runs. A `BuildWaitError` still just ends the cycle.
- [ ] `tests/watcher-parallel-changes.test.ts` proves every scenario below. Build each project as `tests/stack-overlap-cut.test.ts` does: a git repo with `vcs.enabled`, `preSpawnVerify: 'off'`, a `node verify.cjs` verifier that exits 0, and changes approved into worktrees with `approveSpec`. Use one fake adapter that records each spawn's change folder, start and end time, and the most spawns running at once; it holds each spawn until a second spawn runs or a short wait passes, then writes its scoped file and result file. Set `maxConcurrency` on the config object.
- [ ] Every preexisting test passes unchanged, among them the SIGINT test in `tests/watcher-loop-logging.test.ts` and `tests/watcher-abort.test.ts`. If `runWatcherCycle` ends at 80 lines or fewer, remove its key from `tests/function-budget.test.ts`'s grandfather list; change nothing else there.

## Scenarios

- watcher-and-harness: Two independent changes at once
- watcher-and-harness: The cap holds
- watcher-and-harness: One lane runs as before
- watcher-and-harness: A stacked change waits
- watcher-and-harness: A pause stops new starts
- watcher-and-harness: Lanes outlive a cycle
- watcher-and-harness: A new build waits for running lanes
- watcher-and-harness: Abort waits for running lanes

## Details

`ChangeLanes` keeps promises only so the watcher can wait for them. What runs
stays on disk as the running locks, so nothing here changes the reaper, the
locks or any marker.

The pause scenario writes `.run/paused.md` with `writeUsagePause` into the
change folder inside the change's worktree (`worktreePath` from
`src/core/vcs/worktree.ts`), with source `harness`.

For "A new build waits for running lanes", give `startWatcher` a `buildCheck`
that returns null until a task has spawned and then throws
`BuildChangedError` from `src/watcher/service-build.ts`, and an `exit` that
records when it was called.

The new files stay under 250 lines each; `loop.ts` stays on the line-budget
allow list.
