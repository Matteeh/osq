## Changed

- `src/core/status/next-step.ts`: imports `formatPauseUntil` and
  `readActivePause` from `../run/usage-pause.js`. In the `running` branch of
  `readActiveNextStep` it reads `readActivePause(folderPath, Date.now())` and
  sets `detail` to `paused until <formatPauseUntil(until)>` when a pause is
  active, else null. State and command are unchanged. `readNextStep` keeps its
  `@scenario` tags and gains `@scenario status-inspection: Paused format` and
  `@scenario status-inspection: Passed pause format`. No other state branch is
  touched.
- New `tests/usage-pause-next-step.test.ts`: two cases, `Paused format` and
  `Passed pause format`. Each builds an approved active change `007-pricing`
  with a pending task, writes `.run/paused.md` through task 2's
  `writeUsagePause` (until `2099-01-01T09:30:00.000Z` for paused, then
  `2000-01-01T00:00:00.000Z` for passed), and asserts `readNextStep`'s state,
  command and detail plus `formatNextStep`'s exact text from the scenarios. It
  then runs the real `osq show 007` and `osq status` in-process through
  `showCommand` and `statusCommand` with string writers and asserts the exact
  `Next:` and `  next:` lines the scenarios give (and that a passed pause prints
  no `paused until`).

Both the task verify
(`node --import tsx --import ./tests/git-test-env.ts --test tests/usage-pause-next-step.test.ts`)
and the proposal verify (`pnpm verify`) pass.

  test does not invoke the CLI commands; it calls `getSpecDetails` /
  `formatShowText` and `getStatusOverview` / `formatStatusOverview`. I used the
  actual command functions `showCommand` and `statusCommand` (in-process, with
  string writers), which is closer to "the real `osq show` and `osq status`"
  while still matching the scenario text. The result file notes this so a
  reviewer can redirect the test if the intended seam was the core status
  functions.
