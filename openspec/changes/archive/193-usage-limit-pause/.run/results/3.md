## Changed

- New `src/watcher/usage-pause.ts`: the watcher side of the pause, built on
  task 2's `src/core/run/usage-pause.ts` (not changed). It exports
  `recordUsagePause(folderPath, stream, pause, logger?)` (writes `.run/paused.md`
  with `writeUsagePause`, appends the `paused` event through
  `appendHarnessEvent`, and logs `${resolveSymbol('⏸', '[paused]', …)} task <n>
  of <id> paused until <time> (usage limit)`), `pauseTaskOnUsageLimit(folderPath,
  taskNumber, config, logger?)` (reads the current attempt's events, the ones
  after its last `started`, and with a `usage_limit` writes the pause through
  `pauseUntil` with `config.gates.usageLimitWaitSeconds` over
  `DEFAULT_GATES_CONFIG.usageLimitWaitSeconds` and returns the failed
  `RunTaskResult`), `findActivePause(changes, now)`,
  `removePassedPauses(changes, now)`, and
  `discardPausedWorktreeChanges(change, config)` (through `selectVcs`,
  `vcs.status()` and `vcs.discard`; no patch, no commit). Every exported
  function carries its `@scenario` lines.
- `src/watcher/outcome.ts`: `RunTaskResult` gains optional
  `paused?: { readonly until: string }`.
- `src/watcher/spawn.ts`: `spawnTaskAgent` calls `pauseTaskOnUsageLimit` right
  after it records the `exited` event and before its exit-code check. On a
  result it returns `{ ok: false, result: paused }` (a failed outcome with no
  `reason`) and never calls `logOutcome`. Its doc comment gained the three
  pause `@scenario` tags.
- `src/watcher/loop.ts`: at the top of the cycle, `removePassedPauses` once for
  `activeChanges`; at the top of the pending-change branch, `findActivePause`
  and `continue` while any change holds a pause; the steering branch runs
  `runAutoSteer` only when no pause holds and still skips the change; the
  task-failure branch gains `else if (taskResult.paused)` that discards a
  worktree change's edits outside the change folder and writes no dead commit
  and no `halted` line.
- New `tests/usage-pause-watcher.test.ts`: seven cases. Three drive
  `spawnTaskAgent` with an adapter that appends the `usage_limit` event after
  `onSpawn` (reset time, no reset time with `usageLimitWaitSeconds` 600, and an
  earlier attempt's limit). Two drive `runWatcherCycle` for "Another change
  waits" and "Task runs after the reset", and one worktree cycle proves the
  agent's edit outside the change folder is discarded and the branch keeps its
  `osq: 001 approved` tip.

## Deviated

- `spawnTaskAgent` delegates the whole pause to `pauseTaskOnUsageLimit`, which
  returns the failed `RunTaskResult`, instead of building
  `{ success: false, paused: { until } }` inline. Behavior is identical, but
  the inline form pushed `src/watcher/spawn.ts` over the separate 200-line
  runner-lifecycle budget that `tests/import-graph.test.ts` enforces. To make
  room for the three `@scenario` tags on `spawnTaskAgent` while staying under
  that budget I also condensed two preexisting comments (`readRetryContext`'s
  and `ensureTaskResult`'s) in the same file; no code changed there.
- The pending-change pause check sits at the top of the pending branch, before
  the worktree sync, rather than only immediately before the audit and
  `runTask`, so a paused change starts neither the sync nor the task.
- The tests are plain `node:test` cases, not the `scenario(...)` helper,
  because `lookupScenario` throws for every watcher-and-harness scenario (the
  living spec defines `Native model` twice). Expected values are read from the
  delta scenarios. Tasks 1 and 2 hit the same and recorded it.

## Outside scope

- `openspec/specs/watcher-and-harness/spec.md` still defines the scenario
  `Native model` twice, which makes `lookupScenario` unusable for the whole
  capability. Left alone, as in tasks 1 and 2.
