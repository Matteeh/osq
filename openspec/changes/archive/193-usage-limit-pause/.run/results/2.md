## Changed

- New `src/core/run/usage-pause.ts`: owns `<changeFolder>/.run/paused.md`
  (`usagePausePath`). `findUsageLimit` reads the data of the last
  `usage_limit` event from plain records (`{ resetsAt?, error? }`, or
  undefined without one). `pauseUntil(limit, now, waitSeconds)` returns the
  reset time with source `harness` when it parses later than `now` (epoch
  milliseconds), else `now` plus `waitSeconds` with source `wait`.
  `writeUsagePause` writes YAML frontmatter (`task`, `until`, `source`, all
  quoted so a task number reads back as a string) through `parseFrontmatter`'s
  format and the limit's error, or `usage limit reached`, as the body.
  `readUsagePause` returns null for a missing or malformed file (a non-string
  `task`/`until`, an unparseable `until`, or an unknown `source`); a body that
  is the default text reads back with no `error`. `readActivePause` returns it
  only while `until` parses later than `now`. `formatPauseUntil` renders UTC
  `YYYY-MM-DD HH:MM UTC`. The module imports only from `../spec/parser.js`.
- `src/core/foundation/config-gates.ts`: `GatesConfig` gains
  `usageLimitWaitSeconds?: number`, `DEFAULT_GATES_CONFIG` sets it to 1800,
  `validateGatesConfig` reads it through `nonNegativeInteger`, and the module
  comment gains one sentence. `validateGatesConfig` carries the two
  cli-foundation `@scenario` tags.
- New `tests/usage-pause-marker.test.ts`: plain `node:test` cases proving every
  row of "Pause times", "Active pause", "Unreadable marker" and "Last limit
  wins", plus the "Usage limit wait default" and "Invalid usage limit wait"
  cases through `defineConfig` and `validateGatesConfig` with a negative, a
  fractional and a string value. Every expected value is taken from the delta
  scenarios.
- Nothing reads the new module or key yet; no watcher, status or report file
  changed, and every existing test passes unchanged.

## Deviated

- The traceability protocol asks every scenario to be proven with `scenario(...)`
  from `@matteeh/osq/testing`. That helper is unusable for both capabilities
  this task proves: `lookupScenario` throws
  `The watcher-and-harness spec has two scenarios named "Native model"` and
  `The cli-foundation spec has two scenarios named "Explicit settings win"`,
  because each living spec defines one scenario name twice. Editing a living
  spec is out of scope, and neither capability is opted into
  `traceability.capabilities` (osq's own config opts in only `traceability`),
  so the tests are plain `node:test` cases whose expected values come from the
  delta scenario tables. The exported functions still carry their `@scenario`
  tags.
- `writeUsagePause` quotes `source` as well as `task` and `until`, because it
  uses one YAML string style for the block; the acceptance only requires
  `task` and `until` to be quoted, and an unquoted `source` would have been
  fine too.

## Outside scope

- `openspec/specs/watcher-and-harness/spec.md` defines the scenario `Native
  model` twice, and `openspec/specs/cli-foundation/spec.md` defines `Explicit
  settings win` twice. This makes `lookupScenario` unusable for any scenario of
  those capabilities. Left alone, as in task 1.
