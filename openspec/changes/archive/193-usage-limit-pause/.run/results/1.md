## Changed

- `src/harness/types.ts`: added `usage_limit` and `paused` to
  `HarnessEventType`, the new `UsageLimitEventData` (`resetsAt?`, `error?`) and
  `PausedEventData` (`task`, `until`, `source`, `error?`) interfaces, and both
  entries in `OsqEventData`. Nothing writes `paused` yet.
- `src/harness/claude/claude-stream.ts`: `processClaudeStdoutLine` turns a
  `rate_limit_event` whose `rate_limit_info.status` is `rejected` into one
  `usage_limit` event, converting a finite `rate_limit_info.resetsAt` from
  epoch seconds to an ISO time. Any other status falls through to the existing
  verbose `Ignored event` path.
- `src/harness/codex/codex-stream.ts`: `processCodexStdoutLine` still sets
  `state.terminalFailure`, and now appends one `usage_limit` event with the
  message as `error` when the terminal-failure message contains
  `hit your usage limit` (matched without the apostrophe). Added the
  non-exported `emitCodexUsageLimit` helper to keep the function inside the
  80-line budget.
- `src/harness/opencode/opencode.ts`: `processOpencodeStdoutLine` turns an
  `error` event whose `error.type` is `provider.quota` into one `usage_limit`
  event with `error.message` as `error`; any other `error` event keeps today's
  unknown-event path. Added the non-exported `emitOpencodeUsageLimit` helper so
  `processOpencodeStdoutLine` stays under 80 lines.
- `tests/usage-limit-events.test.ts`: replays every row of "Usage limit
  records" through the three stdout functions for task `1` in a fresh temporary
  change folder and checks the task's events, and proves "Codex limit still
  fails the turn" by asserting `state.terminalFailure` keeps the message after
  the line.
- Every changed exported function carries
  `@scenario watcher-and-harness: Usage limit records`; the Codex function also
  names "Codex limit still fails the turn".

## Deviated

- The traceability protocol asks every scenario to be proven with `scenario(...)`
  from `@matteeh/osq/testing`. For `watcher-and-harness`,
  `lookupScenario` throws `The watcher-and-harness spec has two scenarios named
  "Native model"` on every lookup, because the living watcher-and-harness spec
  defines a scenario named `Native model` twice. Editing a living spec is out
  of scope and the capability is not opted into `traceability.capabilities`, so
  I wrote plain `node:test` cases whose expected values are read from the delta
  scenario table instead of using the helper.

## Outside scope

- `openspec/specs/watcher-and-harness/spec.md` has two scenarios named
  `Native model` (in "Codex execution attribution" and "Pi execution
  attribution"), which makes `lookupScenario` unusable for any
  watcher-and-harness scenario. Left alone.
