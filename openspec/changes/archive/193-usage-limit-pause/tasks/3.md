## Acceptance

- [ ] New `src/watcher/usage-pause.ts` holds the watcher side of watcher-and-harness "Usage limit pause" and "Usage limit wait across changes", built on task 2's `src/core/run/usage-pause.ts`, which this task does not change. It exports:
  - `recordUsagePause(folderPath: string, stream: string, pause: UsagePause, logger?: Logger): Promise<void>` writes `.run/paused.md` with `writeUsagePause`, appends the `paused` event to `.run/events/<stream>.jsonl` through `appendHarnessEvent`, and logs `task <n> of <id> paused until <time> (usage limit)`. Log `<n>` as the pause's `task`, `<id>` as the folder's leading number, and `<time>` with `formatPauseUntil`. Use `resolveSymbol('⏸', '[paused]', …)` as the prefix, as the other watcher lines use their symbols.
  - Add whatever else the loop needs in the same module: pausing a task after its run, finding a pause any active change holds, removing passed pauses, and discarding a worktree's edits outside the change folder.
- [ ] A task attempt's events are those after its last `started`, as `findOpenProviderRetry` in `provider-outage.ts` reads them. `spawnTaskAgent` in `spawn.ts` checks them right after it records the `exited` event and before its exit-code check. On a `usage_limit` event, it pauses with `pauseUntil`, `gates.usageLimitWaitSeconds` and `DEFAULT_GATES_CONFIG` as the fallback. It then returns a failed outcome whose result carries `paused: { until }` and no `reason`. It does not call `logOutcome`, so no dead line is printed.
- [ ] `RunTaskResult` in `outcome.ts` gains an optional `paused?: { readonly until: string }`. `runTask` in `runner.ts` already returns `spawnTaskAgent`'s result unchanged, and this task does not edit it.
- [ ] In `runWatcherCycle` in `loop.ts`:
  - Remove passed pauses once per cycle, before the loop over changes.
  - Right before the pre-dispatch audit and `runTask` of a pending change, look for an active pause across `activeChanges`. While one exists, skip that change's spawn without a log line.
  - Do the same right before `runAutoSteer`. The steering change is still skipped afterwards, as today.
  - On a result with `paused`, a worktree change discards what the agent changed outside the change folder. Do it the way `commitDeadTask` in `dead-commit.ts` does, through `selectVcs`, `vcs.status()` and `vcs.discard`, but write no patch and make no commit. Then continue without the dead commit and without the `halted` line.
  - `loop.ts` is on both budget lists; keep the additions to a few lines each.
- [ ] New `tests/usage-pause-watcher.test.ts` proves "Limit with a reset time", "Limit without a reset time" and "Limit from an earlier attempt" through `spawnTaskAgent` or `runTask`, with an adapter that appends the `usage_limit` event to the task's stream before it exits. It proves "Another change waits" and "Task runs after the reset" through `runWatcherCycle`, as `tests/blocked-exit.test.ts` drives cycles. Add one worktree case modelled on `tests/worktree-run.test.ts`: a paused task's edit outside the change folder is gone, and the branch has no new commit. Take expected values from the scenarios.
