## Changed

- `src/cli/inbox-dispatch.ts`: `InboxDispatchOptions` gains `home?: string`. `inboxDispatchCommand` resolves `home` (`options.home` defaulting to `os.homedir()`) and one `stderr` (`options.stderr` defaulting to `console.error`), then:
  - runs the card session with `createWaitRecorder(cwd, 'cards', { home, stderr })` and `home` in `sessionOptions`;
  - runs `--follow` with `createWaitRecorder(cwd, 'follow', { home, stderr })` and `home` in `followOptions`;
  - reads the printed text through `readDispatch(cwd, config, home)` and `--json` through `readDispatchQueue(cwd, config, home)`, so neither writes. The refused `--follow --json` still returns before any recorder is built.
- Added `tests/inbox-wait-log.test.ts` covering every scenario of "Inbox wait log wiring" with an injected terminal/session, scripted keys, a fake watcher, an immediate debounce clock, a manual poll timer, and a fixed clock: the session log (`start`, `seen` `unobserved: true`, `top`, `opened`, `stop`), the follow log (`start` mode `follow` and `stop`), that printed and JSON runs leave the home's `.osq` absent, and that the printed order puts the earlier first-seen change id first.
- `tests/inbox-cards.test.ts` and `tests/inbox-follow.test.ts`: each creates a temporary `home` per test, removes it after, and passes it to the `inboxDispatchCommand` call that runs the card session / `--follow`. The refused `--follow --json` call is left without a home, as the task allows.

## Deviated

- I added one synchronization line to `tests/inbox-follow.test.ts` beyond the temporary `home`: `await settle(() => calls.length >= 1)` before emitting the watcher event. Wiring a recorder makes `followDispatch` await its start `observe` (an extra filesystem round-trip) before it calls `watchDispatch`, which exposed a latent race in the existing test: `settle` on the "Waiting for new items" line could return before the fake watcher existed, so `scheduler.fire()` found no pending debounce timer. The assertion set is unchanged; the extra line only waits for the watcher the test then drives. Without it the preexisting test fails deterministically under the new wiring.
- `createWaitRecorder` is created inside `sessionOptions`/`followOptions`, so it is only built on the paths that actually record; the printed/JSON and refused paths never construct one.
