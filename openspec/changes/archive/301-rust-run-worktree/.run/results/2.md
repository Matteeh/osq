## Changed

- Added `crates/features/run/src/feature/worktree.rs`: `git_on` decides git
  is on only when `vcs.enabled` and `GitVcs::root` in the root canonicalizes
  to the root itself; `find` builds `change_trees` from `worktree_list` with
  the config's timeouts and no stacked folders, matches the id against
  `list_tree_changes` as "Approve lookup" does, and returns the change with
  the root of the tree that holds it.
- `refusals::check` now returns the tree's root with the entry and config:
  with git on it finds the change through `worktree`, otherwise it finds it
  in the root as before, and the git check runs against the tree's root.
- `run::run_one` passes that tree's root to `after_lock`, so the executor's
  folder, the prompt, the scope snapshots and both verifies all run in the
  change's worktree. No commit is made; task 3 adds it.
- `find::names` exposes the existing `matchesFolder` match for the worktree
  lookup.
- Added `crates/features/run/tests/run_worktree_tree.rs` with "Worktree run
  finds its tree", plus lookup cases for an unknown id, an archived folder
  and git off with a worktree naming the change, so every new line has a
  test.
- Added `crates/features/run/tests/worktree_support/mod.rs`, which builds a
  scratch repository from the run fixture: git on with the author, the
  `trees/001-a` worktree on `osq/001-a` holding the approved change, and the
  checkout without the change.

## Deviated

- The tree is the one with the longest root prefixing the change's path, not
  the first one. The scenario's worktree lives at `<scratch>/trees/001-a`,
  inside the checkout, so the root's path prefixes it too; first-match picked
  the checkout and ran the executor there.
- The worktree's approval commit is `--allow-empty`: the change is already in
  the worktree's base commit and the fixture's `.gitignore` ignores `.run/`,
  so writing the seal leaves nothing to commit, but tasks 3 and 4 need the
  approval commit as their tip.
- The extra lookup cases are in `run_worktree_tree.rs` because
  `tests/support/mod.rs` and the other run test files stay unchanged.

## Missing context

- The delta says the change sits in the tree "whose root its path starts
  with" without saying what to do when more than one root does, as the
  scenario's nested worktree makes happen. I chose the deepest root.
