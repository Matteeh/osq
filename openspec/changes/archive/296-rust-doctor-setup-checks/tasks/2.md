## Acceptance

- [ ] `doctor` prints the `managed-blocks` line after its pi lines and the git lines after its change lines, as rust-doctor "Doctor managed blocks", "Doctor git checks" and the modified "Doctor pi checks" and "Doctor change checks" say. It still fails only when a line starts `[fail]`.
- [ ] `crates/features/doctor/src/doctor/managed/` holds `agents-block.txt`, `planner-block.txt` and `claude-plan-command.txt`, and `crates/features/doctor/tests/fixtures/managed/` holds a second copy of each. Every copy is byte for byte the file of the same name in this change's `golden/` folder, with no trailing newline added.
- [ ] `crates/features/doctor/tests/doctor_checks.rs` proves the modified "Doctor checks with a fake pi", and `crates/features/doctor/tests/doctor_changes.rs` proves the modified "Doctor change lines" and "Doctor reads every worktree". Each row's root gets the managed files and `git init`, and nothing else in either file changes.
- [ ] New `crates/features/doctor/tests/doctor_setup.rs` proves "Doctor managed block lines", "Doctor git lines" and "Doctor git environment", each row in its own scratch root, each test's doc naming `Covers: rust-doctor/<scenario>`.

## Details

Put the managed check in a new `src/doctor/managed.rs`. It loads the three
canonical blocks with `include_str!` from `src/doctor/managed/`, and holds
the problem rules and the line builder as small pure functions. Put the git
lines in a new `src/doctor/git.rs`: one reader gathers the facts through
rust-vcs's `Vcs` reads, and the line builders are pure. Build the
`GitVcs` with `GitVcs::new(..).with_timeouts(&config.timeouts)`, as
`changes.rs` does. Take the real path as `change_lines` in `changes.rs`
does. Read the git-env variables from the environment map `run_doctor`
already collects. In `run_doctor` in `src/doctor.rs`, add the
managed-blocks line before `change_lines` and the git lines after them,
using the config `collect_lines` returns. Leave room after the
managed-blocks line for task 3's `decisions` line.

The TypeScript lockfile list, the commit hook names, the true values of
`commit.gpgsign`, the `.gitattributes` block, the opencode agent name
`osq-coder` and the marker texts are TypeScript's constants, so hold each
as a named constant (ADR 029). `maxListedLineEndings` comes from
`config.limits.max_listed_line_endings`.

In the existing tests, define `<healthy>`, `<config>` and `<git>` as the
modified scenarios do. Add `\n<git>` to the expected text of each
"Doctor change lines" row. Build `<git>` at run time from `git --version`,
and write the managed files from `tests/fixtures/managed/` into each root.
`doctor_reads_stacked_changes` gets the same managed files and expected
lines as "Doctor reads every worktree". Make each repository's first commit
before any hook or `commit.gpgsign` setting is written.

For the git scenarios, run doctor in a child of the test binary, as
`spawn_home_child` in `crates/features/show/tests/show_land.rs` does: the
parent builds the root, then starts `std::env::current_exe()` with
`--exact <test name> --nocapture`, a marker variable naming the row, and
the variables the scenario lists. The child runs doctor and asserts the
row's lines. In the managed and git scenarios, check only the lines each
scenario names.

`src/core/**/*.ts` is in `entry` only to show TypeScript's checks. Never
read anything under `src/` from Rust.

Run the proposal's verify as the watcher does, with
`OSQ_CHANGE=openspec/changes/296-rust-doctor-setup-checks`, so the link
gates see this change's new requirements.
