## Acceptance

- [ ] New `src/watcher/mutation-check.ts` implements the watcher-and-harness delta's "Mutation check after a pass". It reads the task's latest start and end `measures` events from its stream, picks through `mutation-pick.ts`, runs through `mutation-run.ts`, and appends each `mutation_ran` event with `appendHarnessEvent`.
- [ ] `runWatcherCycle` in `loop.ts` calls it through one statement when `runTask` succeeds, before `archiveCompletedSpec`.
- [ ] New `tests/mutation-check.test.ts` runs real tasks through the watcher cycle with a fake adapter that edits a tagged, covered function, and a fake `node` mutation command that writes a fixed report. It covers both scenarios of the requirement and the proposal's "Broken mutation command".
- [ ] The same test shows a task that changes one covered function running the command once with its ranges and tests, a helper in the same file in those ranges, a task that only adds a scenario test mutating the function it covers, `range_unknown`, `report_invalid`, and the change still archiving after a failed check.

## Details

`src/watcher/runner.ts` and the other runner lifecycle modules are at their
line budget, which is why the call goes in `loop.ts`. `loop.ts` is on the
line-budget allow list and `runWatcherCycle` is grandfathered, so add only the
call. `tests/focused-verify.test.ts` from change 082 shows a watcher run whose
agent edits files and a fake command. The fake agent must edit a file inside
the task's scope, so the start event's `functionHashes` differs from the
function afterwards. For the budget scenario, set `budgetSeconds` to 1 and have the fake
command sleep past it, so the test takes about a second. New functions stay within 80 lines and new
files within 250.
