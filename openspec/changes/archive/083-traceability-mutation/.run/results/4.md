## Changed

- New `src/watcher/mutation-check.ts`: `runMutationCheck` runs the
  watcher-and-harness "Mutation check after a pass". It reads the task's latest
  start and end `measures` views from its stream, builds the scenario index
  once, picks through `pickMutations`, and runs the picks in order through
  `runMutationPick` under one shared wall-clock budget (`budgetSeconds`), each
  run's timeout being the budget left. It appends one `mutation_ran` event per
  pick through `appendHarnessEvent` with `file`, `function`, `ranges`,
  `scenarios`, `tests`, `outcome`, `killed`, `survived`, `invalid`, `survivors`,
  `duration`, and `exitCode`. Unknown ranges arrive as `range_unknown` from
  `mutation-run.ts`; a pick left once the budget is spent is recorded as
  `budget` without running; `command_failed`/`timed_out` carry the bounded
  output. Every error is caught, logged, and swallowed, so the task's done
  state, markers, and retries are never touched.
- `src/watcher/loop.ts`: `runWatcherCycle` now calls `runMutationCheck` through
  one statement in the `taskResult.success` branch, before
  `archiveCompletedSpec`.
- New `tests/mutation-check.test.ts`: seven tests run real tasks through
  `runWatcherOnce` with a fake adapter that edits scoped source (or adds a
  scenario test) and a fake `node fake-mutate.cjs` that writes a report derived
  from `OSQ_MUTATE`. They cover: one changed covered function run once with its
  ranges (private helper plus the function) and tests; an unchanged function
  newly covered by an added scenario test; `range_unknown` recorded without
  running the command; `report_invalid`; a broken command recorded as
  `command_failed` while the change still archives; the budget running out
  (first `timed_out`, second `budget`); and `traceability.mutation` unset
  appending no event and running no command.

## Deviated

- The budget clock starts where the check begins, not at task start. The
  requirement says "under `budgetSeconds` of total wall time for the task"; the
  check only exists after the task returns, and the test asserts the budget's
  own behavior (timed-out first pick, budget second pick).
- `mutation-check.ts` owns the `budget` reason itself. Task 3's
  `MutationRunResult` reason union has no `budget` member, so the not-measured
  reason is composed in the watcher and only passed through the event payload.
- The fake command derives the mutant lines from the first range in
  `OSQ_MUTATE` rather than hard-coding them, because the report reader counts
  only mutants whose line falls inside the pick's ranges; the file, statuses,
  and replacements are fixed.
