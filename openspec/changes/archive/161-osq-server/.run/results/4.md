## Changed

- `src/core/run/watch-state.ts`: `WatchRecordName` gains `'server'`; exports `ServerRecord`, `readServerRecord` and `writeServerRecord`, written and judged exactly as the service and watcher records are. The generic writer accepts `ServerRecord`; `removeWatchRecord` and `removeWatchRecordSync` already key off `WatchRecordName`, so both delete `server.json` only when it names the given pid. The record stayed in `watch-state.ts` because it still fits the 250-line budget. `WatchState` and `readWatchState` are unchanged.
- `src/watcher/service-deps.ts` (new): holds `ServiceWorkerSpec`, the internal `PendingTimer`, and the default seams `defaultSpawnWorker`, `defaultSetTimer` and `defaultOnSignal`.
- `src/watcher/service.ts`: exports `SERVER_ROLE_ENV = 'OSQ_SERVER_ROLE'`; `ServiceSupervisorOptions` gains `service?: 'watch' | 'server'`. With `service: 'server'` the supervisor spawns the entry with `server start`, sets `OSQ_SERVER_ROLE=worker`, writes and rotates `server.log`/`server.log.1`, removes `server.json` on stop, and logs `new osq build; restarting the server` and `server exited with <code or signal>; restarting in <n>s`. With no `service` every spawn spec, log line, log path and removed record is exactly as before. `runServiceSupervisor` derives the log path from `watchStateDir`.
- `tests/server-state.test.ts` (new): both "Server state files" scenarios against a temporary home and project, with an injected `isAlive` and `process.pid`, plus a malformed `server.json` reading as null.
- `tests/server-supervisor.test.ts` (new): all four "Server supervisor" scenarios with an injected spawn, timer, clock, signal and exit, plus one server crash restart that logs `server exited with 1; restarting in 5s` to `server.log`.

## Deviated

- `ServiceWorkerSpec` and the internal `PendingTimer` moved to `service-deps.ts` beside the three default seams; `ServiceWorkerSpec` is re-exported from `service.ts`, so the existing `tests/watch-supervisor.test.ts` import and the new test's import are unchanged. The acceptance named only the three functions.
- The new test files use plain `node:test` `describe`/`it` rather than the `@matteeh/osq/testing` scenario helper, because the task verify runs through `node --import tsx` with no built `dist`; this matches the approach task 1 and task 3 took for their capability tests. Each test is named after the scenario it covers, and the touched source functions carry `@scenario`/`@adr` doc tags.
