## Acceptance

- [ ] New `src/core/status/steering.ts` exports `SteeringTriggerName` (`stuck`, `blocked`, `regression`), `SteeringTrigger` with `target`, `trigger`, and `reason`, and `deriveSteering(snapshot)`, which reads only the `ChangeFolderSnapshot` it is given, as the status-inspection delta's "Steering triggers" says. It imports only types from `state.ts`, so the two modules share no runtime import cycle.
- [ ] `steering.ts` also exports `describeTrigger(trigger)`, rendering as "Steering triggers" says, and `steeringMarkerPath(folderPath, trigger)`, which returns `getRegressedMarkerPath` for a `regression` trigger and `getDeadMarkerPath` otherwise. Tasks 2 and 3 use both.
- [ ] `SpecState` gains optional `steering: SteeringTrigger[]`, and `deriveSpecState` sets it only when `deriveSteering` returns a trigger. Every other derived field is unchanged, and `state.ts` stays at or under 250 lines.
- [ ] `runWatcherCycle` skips a change whose state has `steering` right after the automatic-retry block and before the worktree block that restores archive specs, commits pending tasks, and checks the tree, as the watcher-and-harness delta's "Watcher leaves a change that needs steering" says. `runWatcherCycle` stays in the function-budget grandfather list, so the skip adds lines and moves nothing out.
- [ ] New `tests/steering-triggers.test.ts` covers every scenario of "Steering triggers" with snapshots built in the test, and the three scenarios of "Watcher leaves a change that needs steering" in a temporary git repository.
