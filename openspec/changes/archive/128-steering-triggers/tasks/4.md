## Acceptance

- [ ] New `src/core/spec/approve-steer.ts` exports `approveSteeredChange(projectRoot, change, config, options)`, which does the numbered steps of the spec-lint-and-approve delta's "Approval after steering" and refuses a running task first. It reuses `confirmApproval`, `readBriefHash`, `toIso`, and `writeApprovalSeal` from `approve-worktree-shared.ts`, `findPlanningSessions` and `appendObservedSessions` as `approveIntoWorktree` does, and the worktree's `Vcs` from `selectVcs` to commit.
- [ ] `approve-steer.ts` also exports `retireSteering(projectRoot, config, change, triggers)`. It calls `retrySpec` for each trigger's target in order, then returns the first task of the change's state that is not done, or null.
- [ ] `approveSpec` derives the located change's state right after `findChange`. A change in a worktree whose state has `steering` goes to `approveSteeredChange`. Every other change goes through the existing paths unchanged, except that after `approveInPlace` a change with `steering` has its triggers retired through `retireSteering`.
- [ ] `ApproveResult` gains optional `continuesFrom`, and `osq approve` prints `  Continues from task <n>` after the worktree lines when it is set. The approval that needs no steering prints what it printed before.
- [ ] `tests/dead-marker-retention.test.ts`'s re-seal case writes `.run/regressed/change.md` with `reason: worktree_dirty` in place of the task regression, so it still covers "Reapproval retains active failure" without a trigger. Every other case is unchanged.
- [ ] New `tests/steering-approve.test.ts` covers every scenario of "Approval after steering" and "Running change that needs no steering" in temporary git repositories with `vcs.enabled`. "The run continues" drives `runWatcherCycle` with a fake adapter until the change archives in its worktree.
