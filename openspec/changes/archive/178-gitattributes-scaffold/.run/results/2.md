# Task 2: doctor prints a gitattributes warning naming osq init

## Changed

- Added `src/core/vcs/doctor-gitattributes.ts` exporting `gitattributesWarning(projectRoot)`, which reads `<projectRoot>/.gitattributes` and returns the `gitattributes` check (`ok: true`, `warning: true`) with the exact message `.gitattributes has no current osq line endings block; run osq init` when the file is missing or does not contain `GITATTRIBUTES_BLOCK` (substring check, so a stale block like `* text=auto eol=lf` warns), else null. Tagged `@scenario` for all three scenarios and `@adr 003`.
- `src/core/vcs/doctor-git.ts`: `vcsWarnings` now calls `gitattributesWarning(projectRoot)` after the `git-signing` check and before `lineEndingWarning`, pushing the result only when non-null, so the line appears only with `vcs.enabled` and `GitVcs` and never changes doctor's exit code. The `vcsWarnings` doc comment names the `.gitattributes` block among the version control warnings.
- Added `tests/vcs-doctor-gitattributes.test.ts` with plain `node:test` `it` blocks titled with the scenario names (the `scenario()` helper cannot look up cli-foundation, which has two `Explicit settings win` scenarios). It proves every row of "Gitattributes warning text" (missing, no block, stale block, current block, current block below text) and "Gitattributes with version control off" through `runDoctorChecks`, and "Gitattributes warning keeps exit code" through `doctorCommand` in an otherwise healthy repository, asserting the check sits after `git-signing` and before `git-line-endings` when all three appear. Repositories, config files, and the healthy project are built the way `tests/vcs-doctor-warnings.test.ts` does.

Both the task verify (`node --import tsx --import ./tests/git-test-env.ts --test tests/vcs-doctor-gitattributes.test.ts`, 3 pass) and the proposal verify (`pnpm verify`, exit 0) are green.
