# Task 1: osq init keeps the line endings block at the top of .gitattributes

## Changed

- Added `src/core/foundation/gitattributes-block.ts` exporting `GITATTRIBUTES_START_MARKER`, `GITATTRIBUTES_END_MARKER`, `GITATTRIBUTES_BLOCK` (the three lines joined with `\n`, no trailing newline), and `writeGitattributesBlock(projectRoot)`, modeled on `writeRulesBlock`/`findRulesRange`. It writes `B\n` for a missing or empty file, prepends `B\n\n` for a file without a block, replaces a stale block in place byte-for-byte elsewhere, leaves a current block untouched, and returns true only when it wrote the file.
- `src/core/foundation/init.ts`: `InitResult` gained `updatedGitattributes`; the managed-block writes moved from `scaffoldProject` into a private `writeManagedBlocks` helper (including the new `writeGitattributesBlock` call), keeping `scaffoldProject` at 70 lines. `scaffoldProject` carries `@scenario`/`@adr 003` tags.
- `src/cli/init.ts`: `initCommand` prints `  updated  .gitattributes (line endings)\n` after the project rules line when `result.updatedGitattributes` is true; tagged `@scenario`/`@adr 003`.
- `.gitattributes`: the managed block plus one blank line at the top, the four original lines unchanged below.
- `README.md`: added `.gitattributes *   a managed block, * text=auto, so git stores text files with LF` directly after the `.env.example *` line in `## What it puts in your repo`.
- Added `tests/init-gitattributes.test.ts` proving every row of "Gitattributes block written by init" and "Gitattributes block on a second init" through `initCommand` in temporary directories with the `stdout` writer, plus repository checks that `.gitattributes` starts with `GITATTRIBUTES_BLOCK` and README holds the new line.

Both the task verify (`node --import tsx --import ./tests/git-test-env.ts --test tests/init-gitattributes.test.ts`, 4 pass) and the proposal verify (`pnpm verify`, exit 0) are green.
