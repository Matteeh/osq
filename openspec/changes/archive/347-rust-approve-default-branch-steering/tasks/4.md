## Details

Put the conflict handling in its own module beside task 3's approval: one
pure function sorts the conflicted paths into planning paths and owned
paths, with rust-core `scope_covers_path` over each task file's `scope`,
one pure function picks the reopened and kept tasks, one formats the task
lists and the `  Reopened ` line, and one orchestrator calls rust-sync
`sync_change_taking_default`, renames the done markers and appends the
`retry` lines. Read the task files with rust-specs `read_task_file`, in
the task order rust-storage `read_change` gives.

The ordinal and the `retry` line follow rust-retry "Retry record"; its
`record.rs` is in `entry` only so you can port the ordinal rule. Never
depend on the retry crate. Write the `retry` line through rust-core
`Envelope` and `event_line`.

Build the repositories as task 3's `approve_default_branch.rs` builds
`requirement-001`, then change them as each scenario's WHEN says before
the branch's commit and `main moved`. Port the helpers you need into the
new file rather than importing that test. The test calls the feature's
`run`, so no event is delivered and `.run/regressed/change.md` keeps its
`sync_conflict` marker after a reopen.

When the mutation check reports a missed mutant, add a test case for that
line. Run the proposal's verify as the watcher does, with
`OSQ_CHANGE=openspec/changes/347-rust-approve-default-branch-steering`, so
the link gates see this change's new requirements.
