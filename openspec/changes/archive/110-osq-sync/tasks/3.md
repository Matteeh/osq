## Acceptance

- [ ] New `src/core/vcs/sync-change.ts` exports `syncChange`, following the version-control delta's "Sync on request". It finds the change with `listChanges` and `matchesFolder` as `resolveChange` in `src/core/vcs/land.ts` does. It checks a running task with `deriveSpecState` and `readChangeFolder`, and a stacked dependency with `awaitedDependencies`. On a stop of an active change, it appends the `sync_stopped` event with `fs` directly, as `appendSyncEvent` in `sync-main.ts` does, reading the reason from task 1's `SyncStop`.
- [ ] New `src/cli/sync.ts` exports `syncCommand` and `registerSyncCommand`, following the cli-foundation delta's "Sync command" and shaped like `src/cli/land.ts`. `createProgram` in `src/cli/index.ts` registers it next to `registerLandCommand`.
- [ ] README's version control section gains one paragraph after the `osq message` paragraph and before "Working with version control on". It says that the watcher merges the default branch into a change's branch before its first task and before archive, as `osq: <id> sync <default branch>`, when the default branch has moved. It says a conflict in living specs or the archive is resolved from the default branch, that any other conflict halts the change with `sync_conflict` naming the files, and that a red verify or a requirement the default branch changed halts it with `sync_failed`. It says that `osq sync <id>` does the same on request and refuses while a task runs. It also says that a stopped `osq sync` halts nothing and records a `sync_stopped` event, which `osq status` shows. The numbered walkthrough is unchanged.
- [ ] New `tests/vcs-sync-command.test.ts` covers every scenario of "Sync on request" and "Sync command" on real temporary repositories.
- [ ] `tests/readme-land.test.ts`, `tests/own-vcs-config.test.ts`, `tests/cli.test.ts`, and every other test pass unchanged.

worktree, `runWatcherOnce` for a verified task, and a commit on `main` in
the checkout to move the default branch. For "Task running", write a lock
for the change's next task under its worktree folder's `.run/running/` with
the test process's own pid, as a live runner would.
