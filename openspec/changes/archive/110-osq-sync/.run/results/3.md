## Changed

- `src/core/vcs/sync-change.ts`: new `syncChange(projectRoot, config, id, progress)`. It
  refuses `vcs.enabled` off or `NoVcs` (`osq sync needs vcs.enabled and git`), then finds the
  change with `listChanges`/`matchesFolder` as `resolveChange` does, then refuses a running
  task via `deriveSpecState`/`readChangeFolder`, an awaited dependency via
  `awaitedDependencies`, and a dirty worktree (paths outside the change folder's `.run/`
  other than its `tasks.md`). Otherwise it runs `syncWithDefaultBranch` and returns
  `Synced osq/<folder> with <default branch>` or `osq/<folder> already has <default branch>`.
  A stop of an active change appends a `sync_stopped` event (`reason`, `message`,
  `defaultBranch`) with `fs` and throws; an archived change appends nothing.
- `src/cli/sync.ts`: new `syncCommand` and `registerSyncCommand`. The command prints the
  result to stdout, streams progress to stderr, exits zero, and prints only a refusal's or
  stop's message to stderr and exits one. It loads `osq.config.ts` inside its error handling.
- `src/cli/index.ts`: registers `sync` next to `registerLandCommand`.
- `README.md`: one paragraph in the version control section, after the `osq message`
  paragraph and before `### Working with version control on`, describing the watcher's two
  syncs, conflict resolution, `sync_conflict`/`sync_failed` halts, `osq sync <id>`, and the
  uncommitted `sync_stopped` event `osq status` shows.
- `tests/vcs-sync-command.test.ts`: new tests over real temporary repositories for every
  "Sync on request" and "Sync command" scenario, plus the no-change, uncommitted-worktree,
  and vcs-off refusals.

## Deviated

The task details said to build active change state with `runWatcherOnce` for a verified
task. A change whose tasks are all verified is archived by that same run, and a two-task
change would have both tasks run and then archive. So the active-change cases approve into a
worktree and write the task's `.run/done/<n>` marker by hand, exactly as the watcher's verify
gate writes it; `syncWithDefaultBranch` then re-runs that task's real `verify`. The
archived and stacked cases still use `runWatcherOnce` and `approveSpec`.

## Missing context

The task said the `sync_stopped` append goes "as `appendSyncEvent` in `sync-main.ts` does",
but no such helper exists there. The event append helper is `appendEvent` in
`sync-verify.ts`, which is not exported. I wrote a local `appendSyncStopped` in
`sync-change.ts` with the same `{ type, timestamp, data }` shape and used `fs` directly.
