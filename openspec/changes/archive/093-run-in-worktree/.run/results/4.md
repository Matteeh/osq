## Changed

- `src/core/lifecycle/reject.ts`: `rejectSpec` now takes `tree` from
  `findChange` and builds the rejected destination from `tree.rejectedDir`,
  reads the change's markers through `readChangeFolder(tree.root, ...)`, and
  shows the collision path relative to `tree.root`. A worktree change is moved
  into the worktree's rejected directory and the checkout is never touched.
- `src/core/lifecycle/retry.ts`: `retrySpec` takes `tree` from `findChange`;
  recertification runs the task's verify with `runVerificationCommand(tree.root,
  ...)` and hashes its scope with `computeTaskScopeHash(tree.root, ...)`.
- `src/core/status/status.ts`: `formatStatusOverview` prints
  `  warning: a task is running in this worktree; do not edit it until the task ends`
  directly below the worktree line when any task of the worktree change is
  `running`, before the checkout-drift warning.
- `tests/worktree-lifecycle.test.ts` (new): four `node:test` cases over a real
  temporary repository with a change approved into a linked worktree — reject,
  retry recertification, manual done, and the running-task warning. Each
  snapshots the checkout's change folder and asserts it is byte for byte
  unchanged. The recertification case proves the verify and scope hash ran in
  the worktree: the verifier and the scoped file exist only there, the verifier
  writes `recert-ran.txt` in its cwd, and the refreshed done marker records a
  non-null hash for `src/app.ts`.

## Deviated

- The running-task warning is derived from the existing derived task state
  (`spec.tasks.some((task) => task.status === 'running')`) rather than a new
  field on `ChangeWorktree`. Status already reads `.run/running/` from the
  located folder's tree, so no extra read is needed and the warning follows the
  same liveness view the rest of status shows. The test takes the lock with
  `acquireLock`, which writes the canonical JSON lock rather than a bare pid.
