## Acceptance

- [ ] `rejectSpec` commits and removes a worktree change, and withdraws a stacked change, as the watcher-and-harness delta's "Rejection under version control" says. The commit and removal live in new `src/core/lifecycle/reject-vcs.ts`, and `RejectResult` gains optional fields for the worktree outcome, the kept branch, and the withdrawn stacked path.
- [ ] `osq reject` prints the `Worktree removed:`, `Worktree kept:`, `Branch kept:`, and `Withdrew stacked approval:` lines that requirement names; with `vcs.enabled` off its output is unchanged.
- [ ] `tests/worktree-lifecycle.test.ts` changes only its reject case, which now reads the rejected folder at the branch with `git show`, as the modified "Reject a dead change in a worktree" scenario says.
- [ ] README.md's "Version control" section describes stacking as this change's Goal does. It drops the sentence saying stacking is not implemented, describes reject's commit and worktree removal, and adds `dependency_changed`, `dependency_diverged`, and `stack_cut_failed` where it lists the halt reasons.
- [ ] New `tests/reject-worktree.test.ts` covers every scenario of "Rejection under version control".

## Details

Build the commit the way `commitArchive` in `src/core/run/task-commit.ts`
does: select the `Vcs` on the worktree root and pass the status paths under
the old folder and the rejected folder, relative to `vcs.root()`. Build the
message with `formatCommitMessage` and `readCommitTrailers`. A failed commit
or `worktreeRemove` becomes the `why` of a kept worktree, never a thrown
error, because the folder has already moved. A stacked change's tree has
`stackedFolder`; delete its `root`.

For "Not recreated after reject", call `recreateWorktrees` from the checkout
after the rejection and assert that it returns no lines and creates nothing.
For the stacked case, make a stacked approval halt as
`tests/stack-run.test.ts` does, or write its `.run/regressed/change.md`
directly.
