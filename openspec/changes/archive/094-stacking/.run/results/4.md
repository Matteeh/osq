## Changed

- New `src/core/spec/stack-cut.ts`:
  - `decideStackCut` reads `.run/stacked-on` and each dependency's state
    through `stack-dependencies.ts` and returns `wait`, `halt` with a
    `dependency_changed`/`dependency_diverged` reason and detail, or `cut`
    with a base, exactly as the watcher-and-harness delta's "Stacked cut" says:
    unapproved or hash-changed halts, any approved waits, all landed cuts from
    the default branch, else the first archived dependency whose branch holds
    every other archived dependency's archive, else diverged.
  - `cutStackedChange` creates `osq/<folder>` at the base unless it exists,
    adds the worktree at `worktreePath` unless a worktree has the branch, runs
    `runPrepare` there, and unless the branch tip already holds
    `<changes>/<folder>/.run/approved` replaces the worktree folder with the
    stacked copy, writes `.run/base` with the worktree HEAD, and commits
    `osq: <id> approved` with `vcs.author`. It then deletes the stacked
    approval directory and returns the worktree path.
- New `src/watcher/stack-run.ts`: `runStackedChanges` visits every active
  change in a stacked tree in numeric order, skips one with
  `.run/regressed/change.md`, and waits, halts, or cuts it, logging
  `stacked <folder> on <base>: worktree <path>`. A failed cut halts with
  `stack_cut_failed` and the error's message. With `vcs.enabled` off or under
  `NoVcs` it returns without doing anything.
- `src/watcher/worktree-run.ts`: `WorktreeHaltReason` gains
  `dependency_changed`, `dependency_diverged`, and `stack_cut_failed`.
  `haltWorktreeChange` is reused unchanged to write the stacked copy's
  `.run/regressed/change.md`, its `regressed` event, and its halt line.
- `src/watcher/loop.ts`: `runWatcherCycle` calls `runStackedChanges` once,
  before it lists changes.
- New `tests/stack-run.test.ts`: the six "Stacked cut" scenarios (chain cut
  from the dependency archive commit with `.run/base` naming its parent,
  pending dependency waits, landed-by-hand cuts from `main`, two archived
  dependencies diverge, failed prepare halts and resumes, flag off does
  nothing) and the three "Stacked halt" scenarios (rejected dependency,
  changed recorded hash, re-approval clears the halt and cuts at HEAD).

## Deviated

A failed cut removes the worktree it added (and prunes git's record) before it
rethrows, keeping the branch and the stacked approval. The delta says the next
cycle "reuses the branch and worktree that exist", but `changeTrees` prefers
any worktree whose branch is `osq/<folder>` over the stacked directory even
when that worktree holds no change folder. Leaving the failed worktree would
hide the stacked tree, so neither the next cycle nor `retrySpec` could find the
change. Removing the worktree keeps the branch and lets the next cycle re-add
it; the failed cut's test passes with the branch reused.

## Missing context

The planner may want task 2's "Change locations" to suppress a worktree tree
only when that worktree actually holds the change folder it names; then the
failed-cut worktree could stay. As written, it suppresses on branch name alone,
which is why the cut cleans up its own failed worktree.
