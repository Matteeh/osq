- [ ] `change_link_gates` follows rust-linter "Change ownership": a capability whose delta ADDS or MODIFIES a requirement named `Code ownership` owns the globs `code_ownership` reads from that requirement's `raw` text, in place of its living globs; every other capability keeps what `read_capability_ownership` gives; the `owns` edges are added in byte order of capability names.

- [ ] New `crates/kernel/linter/tests/link_gates_ownership.rs` proves "Findings of the link gates ownership fixture", "A change moves ownership to a new capability" and "A new capability's ownership overlaps a living one", checking each finding's rule, node, display and fix, and the finding count. ## Details

Today `build_link_graph` ends with `files::add_ownership`, which reads
the living globs itself with `read_capability_ownership`. Have
`add_ownership` take the ownership list instead, and give `build.rs` a
crate-private builder that takes it; `build_link_graph` passes the living
list. `osq_core::Graph` cannot remove an edge, so the change's globs must
go in before the `owns` edges are added, never after.

Reuse `read_delta`, `code_ownership`, `read_capability_ownership` and
`CapabilityOwnership` from `osq_kernel_specs`, and the `folder_names` and
`add_delta_nodes` code already in `gates.rs`. Put the new change code in
`src/gates/change.rs` if `gates.rs` grows past about 220 lines. Match the
requirement name exactly as the delta parser gives it, `Code ownership`.

The fixture is data: it is never built, and `cargo fmt` does not reach it.
Never edit it or the scenarios. If a finding differs, the code is wrong.
`link_gates_change.rs`, `link_gates.rs` and `link_graph.rs` must pass
unchanged.

cargo-mutants runs on every line this task changes. Before exiting, run
`cargo mutants -p osq-kernel-linter -f <file> -o "$(mktemp -d)"` on each
source file you changed, and add a fast test in `link_gates_ownership.rs`
for any survivor.
