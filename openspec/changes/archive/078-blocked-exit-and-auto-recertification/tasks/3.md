## Acceptance

- [ ] `NeedsYouItem` gains optional `blocked?: { readonly need: string }`.
- [ ] New `src/core/status/blocked-item.ts` takes the status overview and the needs-you items. For each `task-dead` item whose task's `deadReason` is `blocked`, it adds `blocked.need` from the task's result file through `parseResultSections`, or `(not stated)` when that is null, and sets the command to `osq reject <id> --reason <text>`. Every other item is returned unchanged.
- [ ] `readInbox` in `inbox-projection.ts` applies it to the projected items, so the CLI and the web transport both get it.
- [ ] `needsYouLine` in `inbox-text.ts` renders a blocked item as the status-inspection delta's "Blocked inbox items" says, with whitespace in the need collapsed to single spaces.
- [ ] New `tests/inbox-blocked.test.ts` covers both scenarios of "Blocked inbox items" and the "Blocked task command" scenario through the real bare `osq --json` and text output, on a temp project whose dead marker has `reason: blocked` and whose result file has a two-line `## Blocked`. It also covers `(not stated)` when the result file has no `## Blocked`.

## Details

`projectNeedsYou` in `inbox.ts` is synchronous and reads only the overview;
the result file read belongs in `blocked-item.ts`, which is async. The task's
`deadReason` comes from `TaskState` in `src/core/status/state.ts`, and each
`SpecState` has its `folderPath`; the result file is `.run/results/<n>.md`
under it. `inbox.ts` is 243 lines and must stay within 250.
`tests/inbox-stuck.test.ts` shows how to build a dead task on a temp project and
read the inbox.
