## Changed

- `src/core/status/inbox.ts`: added optional `blocked?: { need }` to
  `NeedsYouItem`.
- New `src/core/status/blocked-item.ts`: `applyBlockedItems(overview, items)`
  matches each `task-dead` item back to its `TaskState`, and for a task whose
  `deadReason` is `blocked` reads `.run/results/<n>.md` through
  `parseResultSections` (via the `getResultPath` layout helper), sets
  `blocked.need` to the parsed `## Blocked` text or `(not stated)`, and sets the
  command to `osq reject <id> --reason <text>`. Every other item is returned
  unchanged.
- `src/core/status/inbox-projection.ts`: `readInbox` applies `applyBlockedItems`
  to the projected needs-you items (active plus pending-verification), so the
  CLI and web transport share it.
- `src/core/status/inbox-text.ts`: `needsYouLine` renders a blocked item as
  `<task row> — blocked: <need> — reject, then osq plan --next --replan —
  <command>`, collapsing whitespace in the need to single spaces.
- New `tests/inbox-blocked.test.ts`: drives the real bare `osq --json` and text
  output on a temp project with a `reason: blocked` dead marker and a two-line
  `## Blocked`, covers the other dead task staying unchanged with `osq retry`,
  and covers `(not stated)` for a blocked task whose result file has no
  `## Blocked`.

## Missing context

The task said `deadReason` "comes from `TaskState`" but did not name the module.
`TaskState` is exported from `src/core/status/state.ts`, not from `status.ts`;
the import was resolved accordingly.
