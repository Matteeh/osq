## Changed

- `src/core/vcs/land-stop.ts` (new): `recordLandStop(config, change, stop)`
  writes `.run/regressed/change.md` with `reason: <stop reason>` and the stop's
  message, appends the `regressed` event line (`task: change`, `reason`,
  `output`) exactly as `haltWorktreeChange` does, and commits both paths on the
  change's branch with `osq: <id> land stopped` and `vcs.author`. On a failed
  commit it resets the two paths with `vcs.discard`, puts both files back, and
  throws `osq could not record the stop: <git output>`. Also exports
  `recordsLandStop(reason)` for the three steering reasons.
- `src/core/vcs/land.ts`: catches a `SyncStop` around `syncWithDefaultBranch`.
  For `sync_conflict`, `requirement_changed`, or `sync_verify_red` it records
  the stop, then rethrows the sync's message, or that message plus the
  failed-commit line; every other error is rethrown unchanged. 241 lines.
- `src/core/vcs/land-checks.ts`: new `assertNoSteering(change)` derives the
  change's state in its own tree and refuses with `<folder> needs steering:
  <describeTrigger(first)>; run osq plan <id>` when it has `steering`.
  `landChange` calls it after the worktree-clean check and before
  `assertNoEarlierChange`, only for a change that has not landed.
- `tests/vcs-land-steering.test.ts` (new): the three "Land records a steering
  stop" scenarios (conflict, red verify, other stop records nothing) and
  "Recorded stop refuses the next land", through `landCommand` against
  temporary git repositories with `vcs.enabled`.

## Deviated

- On a failed record commit, `recordLandStop` resets the two paths through
  `vcs.discard` before writing the snapshots back, so the index and tree both
  return to their pre-write state and the worktree status stays empty. The
  spec only says "put both files back as they were"; the index would otherwise
  keep the staged versions.

Touched: src/core/vcs/land-stop.ts, src/core/vcs/land-checks.ts, src/core/vcs/land.ts, tests/vcs-land-steering.test.ts
