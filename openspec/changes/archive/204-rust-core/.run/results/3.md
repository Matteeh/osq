# Task 3 result

## Changed

Implemented the seal and the change typestate of `osq-core`.

- `crates/core/src/seal.rs`: `Seal`, `Seal::parse` and `SealError`, with
  `as_str` giving the text after trimming. A seal is `sha256:` and exactly 64
  lowercase hexadecimal digits; anything else is `SealError`. `Seal` also has
  `Display`, and `SealError` has `Display` and `Error`.
- `crates/core/src/change.rs`: the generic `Change<S>` holding its id, its
  task ids and the state `S`; the states `Draft(())`, `Approved { seal }` and
  `Archived(())`, each with only private fields. `Change::draft` is the only
  constructor. `Change<Draft>::approve(recorded, computed)` is the only way to
  a `Change<Approved>` (it stores `recorded` once the seals are equal, else
  `ApproveError::SealMismatch` with both). `Change<Approved>` has `seal`,
  `next_task` and `archive`. `next_task` and `archive` both read
  `change_status` from the `fold` module instead of repeating its order;
  `next_task` returns the `TaskId`-lowest pending id only when the status is
  `Pending`, and `archive` returns `Change<Archived>` only when it is `Done`,
  else `ArchiveError::NotDone(status)`.
- `crates/core/src/lib.rs`: added `pub mod change`, `pub mod seal` and the
  re-exports `Approved`, `ApproveError`, `ArchiveError`, `Archived`, `Change`,
  `Draft`, `Seal` and `SealError`. Nothing else changed.
- `crates/core/tests/gates.rs`: four tests, one per scenario, one case per
  table row — `seal_texts` (6 rows), `approve_checks_the_seal` (2 rows),
  `next_task_of_an_approved_change` (6 rows) and `archive_needs_a_done_change`
  (3 rows). Every event/state is built through the public API only.
- The `Change` doc comment holds the four `compile_fail` doctests for "Gates
  cannot be skipped": building `Change<Approved>` by hand (`E0451`), building
  `Change<Archived>` by hand (`E0603`), `next_task` on a `Change<Draft>`
  (`E0599`) and `archive` on a `Change<Draft>` (`E0599`). Each block is
  otherwise well-typed, so removing that one gate makes it compile.

Every public function's doc ends with `Implements: rust-core/approval-seal`
or `Implements: rust-core/change-typestate`, and every test function's doc
names its `Covers: rust-core/<scenario>` in kebab-case. `cargo fmt --all` ran.

## Deviated

One naming choice a reviewer may notice: for the three public functions that
return `Result` (`Seal::parse`, `Change::approve`, `Change::archive`) I put the
`# Errors` section before the closing `Implements` line, so the doc literally
ends with `Implements:` as the acceptance asks. `parse_event_line` from task 1
keeps `Implements` before `# Errors`; that file is outside this task's scope,
so I left it alone. Both orders satisfy `clippy::missing_errors_doc`.

The `Approved` state literally stores the seal, so `Change<Approved>` "holds
the seal" without an extra field on `Change`. The other two states are unit
tuple structs with a private field, which rustc's `dead_code` lint accepts for
a `()` field while still refusing hand construction outside the crate.
