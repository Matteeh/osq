## Deviations

- **Runner delegates hash/build metadata to `regression.ts`.** The task detail
  said runner computes the scope hash and resolves build info inline. Doing so
  blew the strict 200-line runner budget, so `buildDoneMetadata(projectRoot,
  scope)` lives in `regression.ts` and runner passes its result straight to
  `writeDoneMarker`. Same computed values (`sha256` scope hash, build commit,
  exit code 0).
- **Done marker also records `scope_files`.** The prescribed frontmatter has only
  `scope_hash`/`build_stamp`/`exit_code`, but a combined hash cannot identify
  *which* path regressed. The per-file hash map is emitted as a YAML flow map in
  the same frontmatter (`scope_files: { ... }`) and consumed by
  `checkDoneTasksScopeHashes` to produce `differingPaths`. This is additive; the
  three required fields are unchanged.
- **Pre-spawn regression lifecycle lives in `regression.ts`, not `outcome.ts`.**
  Task 3 owns `writeRegressedMarker`/`recordRegressedEvent` and the
  `HarnessEventType` union, but `runner.ts` is only in this task's scope, so the
  pre-spawn marker/event must be wired here. `recordScopeRegression` writes
  `.run/regressed/<earlierTask>.md` and appends a `regressed` event to
  `.run/events/<earlierTask>.jsonl`. Until task 3 adds `'regressed'` to
  `HarnessEventType`, the event is appended through `appendHarnessEvent` with a
  documented `as unknown as HarnessEvent` assertion so this writer stays on the
  single append path.
- `'regressed'` was added to `RunTaskFailureReason` here (task 3 also plans it).
