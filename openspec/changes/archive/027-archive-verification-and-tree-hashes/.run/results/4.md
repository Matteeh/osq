## Deviated

- **`verify.ts` return shape untouched.** Task detail 3 suggested capturing the
  spawn result directly in `archiver.ts`. Instead the archiver calls the
  existing `runVerificationGate` and recovers its payload from the emitted
  `verify_ran` event, because (a) `src/watcher/verify.ts` is outside this task's
  scope and (b) `tests/runner-synthesized-result.test.ts` pins the gate's return
  object with `deepEqual`. This keeps `verify_ran` on the single emission path
  required by the capability rule.
- **Out-of-scope collateral edits were unavoidable.** Enforcing a non-empty
  proposal `verify` makes `approveSpec` (which calls `lintChangeFolder`) reject
  every existing scaffolded/inline proposal. To keep the suite and the change's
  own archive-time verify green:
  - `templates/proposal.md` and `new.ts`'s `FALLBACK_PROPOSAL_MD` gained
    `verify: node -e "process.exit(0)"` (the same placeholder task files use);
  - inline proposals in `tests/manifest.test.ts`, `tests/runner-scope-hashes.test.ts`,
    `tests/runner-test-gating.test.ts`, and `tests/cut-over.test.ts` gained the
    same line;
  - `tests/fixtures/events/{verified,dead}.jsonl` were regenerated via
    `UPDATE_GOLDEN=1` because the template change shifted `repoLines` (443→444)
    and `proposalWords` (243→247).
  - `tests/archiver.test.ts` needed no edit: its `createNewSpec` proposals and
    task verifies now pass through the template placeholder.
- **Empty legacy change-level verify is skipped** by the archiver so pre-existing
  approved changes with a legacy `spec.md` (no `verify`) still archive. New
  proposals cannot reach approval without one.
