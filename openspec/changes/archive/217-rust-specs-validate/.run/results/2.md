  rename and requirement-rule findings, and the pass order that makes a stable

- `src/validate/delta_scan.rs` (new): the line-accurate delta scan, reusing
  `markdown::delta`'s `split_sections`, `rename_side`, `is_invalid_rename` and
  `removed_bullet_name` and `outline::scan`'s headings and requirement blocks.
  It gives each delta section, requirement, removed name, valid rename side,

- `src/markdown/delta.rs`: made `Section` and its fields, `split_sections`,

  the scan reads the delta lines once, through the parse's own helpers. No
  other change.
- `src/lib.rs`: re-exported `validate_delta`, `check_delta_targets` and
  `validate_change`.
- `tests/validating_deltas.rs`: the "Delta spec findings" table, one case per

## Deviated

- The delta scan lives in `src/validate/delta_scan.rs`, a `delta*.rs` file in
  scope, not in `outline.rs`. Putting it in `outline.rs` took that file to 263
  lines, over the task's 250-line cap; `delta_scan.rs` reuses `outline::scan`
  for the headings and requirement blocks, so nothing is read twice.
- `delta.rs` and the entry/conflict rules are split across `delta.rs` and
  `delta_entries.rs` for the same cap.
- Findings on one line are ordered by a stable sort by line over a fixed pass
  order, not by a code-rank comparator: the passes run outside, headings,
  duplicates, renames, requirement rules, conflicts, and the heading pass
  pushes unknown, then empty, then missing, so every same-line pair comes out
  in the table's order.
- `outline.rs` is byte-for-byte task 1's file; it is listed as touched because
  it was written while moving the scan out.
