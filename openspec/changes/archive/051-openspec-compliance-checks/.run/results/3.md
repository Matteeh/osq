## Changed

- `templates/openspec/schemas/osq/templates/proposal.md` now holds the same
  bytes as `templates/proposal.md`, so both proposal entry points agree.
- `templates/openspec/schemas/osq/schema.yaml`: only the `proposal` artifact's
  `instruction` changed, to the instruction in the task. Every other artifact,
  `apply`, and all remaining bytes are untouched.
- `templates/openspec/config.yaml`: only `rules.proposal` changed, to the two
  rules in the task. `context` and the `specs`/`tasks` rules keep their bytes.
- Added the repository's dogfood copy, each byte-identical to its template
  counterpart: `openspec/config.yaml` and
  `openspec/schemas/osq/{schema.yaml,README.md,templates/{proposal,spec,tasks}.md}`.
- Added `tests/proposal-format.test.ts`: asserts the schema proposal template
  equals `templates/proposal.md`, that the repository config and schema hold the
  same file set and bytes as `templates/openspec/`, that the proposal
  instruction and rules name Goal, Verify, Non-goals, Contract, Human steps, and
  Delta in order with no `What Changes` or `Capabilities`, and that
  `MANAGED_PLANNER_BLOCK` names `## Goal`, `## Non-goals`, and `## Human steps`.
- Regenerated `tests/fixtures/events/verified.jsonl` and `dead.jsonl` with
  `UPDATE_GOLDEN=1`; only the two `repoLines` values per file changed
  (464 -> 495), confirmed by diffing against a pre-run copy.

## Deviated

- The first `rules.proposal` rule contains `in order: Goal, ...`. Written as a
  plain YAML scalar that `: ` makes the line parse as a mapping, not a string,
  which would fail `tests/init.test.ts`'s assertion that every rule is a string.
  The line is therefore double-quoted so `rules.proposal` parses to exactly the
  two rule strings the task names.
- `osq lint` on change 051 still exits 1 for two pre-existing findings that this
  task's `scope` cannot touch: task `2.md` names the now-existing
  `tests/openspec-version.test.ts` without `tests.modify: true`, and
  `openspec validate --specs` reports `INFO Requirement text is very long` for
  the living specs. Both reproduce with `openspec/config.yaml` and
  `openspec/schemas/` moved aside, so they predate this task. `openspec validate
  --changes` reports both in-flight changes valid under the rewritten schema.
  Neither the task `verify` nor `pnpm verify` runs `osq lint`.

## Missing context

- The task's acceptance says `osq lint` on in-flight changes should pass, but the
  two findings above are outside this task's `scope` and predate it. No file in
  scope can resolve them.
