## Details

This task's `scope` is authoritative over any injected code-ownership rules.

Compliance means osq merges exactly what `openspec archive` merges. If a fixture
exposes a divergence beyond the ones listed in the proposal, make osq match
OpenSpec. The one exception is where OpenSpec silently drops content: there osq
refuses, and you record it in `.run/results/1.md`. Do not change
`applyOpenSpecDeltas` in `src/watcher/archiver.ts`; it is the osq entry point
the test calls.

The living specs under `openspec/specs/` must not change. After your merge
changes, replaying the archive in `living-specs-delta-equivalence.test.ts` must
reproduce them byte for byte, apart from the one blank line after `## Purpose`
in capabilities osq created before this change. If the replay differs anywhere
else, stop and write the difference in `.run/results/1.md`. A scan of every
archived delta found no MODIFIED block that drops a scenario and no GIVEN or AND
bullets.

### Fixture layout

Each case is a folder `tests/fixtures/openspec-diff/<case>/` holding:

- `case.json`: `{ "expect": "identical" }`, `{ "expect": "both-refuse" }`, or `{ "expect": "osq-refuses" }`.
- `specs/<capability>/spec.md`: the base living specs, when the case has any.
- `changes/<nnn>-<slug>/`: one or more changes, applied in name order. Each has
  an osq-format `proposal.md` with frontmatter `title`, `depends_on: []`,
  `verify: node -e "process.exit(0)"`, and `features.reads`, plus the sections
  `## Goal` through `## Delta`. Each also has a `tasks.md` whose single box is
  ticked as `- [x] 1. When ...`, a `tasks/1.md`, and its delta specs.

Keep each refusal case to one capability, because `applyOpenSpecDeltas` writes
capabilities one at a time. Base specs follow the living-spec shape:
`# <capability> Specification`, `## Purpose`, `## Requirements`, with
`<!-- source: ... -->` comments under some requirement headers.

### Test procedure

For each case, create two temporary repositories. Copy
`templates/openspec/config.yaml` and `templates/openspec/schemas/` into each
one's `openspec/`, so the case runs under the osq schema users get. Then copy
in the case's `specs/` and `changes/`. The binary is
`process.env.OSQ_OPENSPEC_BIN`, falling back to the repository's
`node_modules/.bin/openspec`. Run it with `OPENSPEC_TELEMETRY=0` through
`execFileSync` or `spawnSync`, never a shell.

- `identical`: for each change in order, first run
  `validate <id> --type change --strict --json --no-interactive` in repository
  A and require exit 0. Then run `archive <id> --yes --json` in A, and
  `applyOpenSpecDeltas(B, <B change folder>, DEFAULT_CONFIG)` in B. At the end,
  the `openspec/specs` trees must hold the same relative paths with
  byte-identical contents.
- `both-refuse`: `archive` exits non-zero, and a `status` entry in its JSON
  output has code `archive_spec_update_failed`.
  `applyOpenSpecDeltas` rejects with `DeltaMergeError`. Both `openspec/specs`
  trees still equal the case's base.
- `osq-refuses`: `applyOpenSpecDeltas` rejects with a `DeltaMergeError` whose
  message contains `### Requirement:`. After `archive` in A, the living spec
  still lacks the rename's target name. That records OpenSpec's silent skip, so
  the scheduled job notices if upstream starts applying it.

Archive folder names differ between the tools, so compare `openspec/specs`
only.
